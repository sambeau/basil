## [Unreleased]

### Breaking Changes
- **Site layout: code and persistent state now have separate anchors (FEAT-152)** — `config.BaseDir` is replaced by two anchors: `ReleaseDir` (the site's code, replaced by every deploy) and `DataDir` (everything that must survive one). Every configured path now resolves against one of them, and **nothing resolves against the process working directory** — starting Basil from a different directory no longer changes where anything lives. Code (`site.path`, `public_dir`, `routes[].handler`, `routes[].public_dir`, `static[].root`, `static[].file`, `error_pages`) resolves against the release; state (`database.path`, the auth database, `https.cache_dir`, `https.cert`, `https.key`, `images.cache_dir`, `dev.log_database`, `logging.output`, `logging.parsley.output`, `security.allow_write`) resolves against the data root.

  **Where things move.** `https.cache_dir` (default `certs`), `https.cert`, `https.key` and `images.cache_dir` previously resolved against the *process working directory*, so where a site's certificates lived depended on where the operator happened to be standing. They now live under the data root. On an existing site, move `certs/` (and the image cache, if you care about it) next to the config, or set `data_dir` to where they already are — Let's Encrypt rate-limits re-issue, so this is worth doing before a restart. `security.allow_write` entries now resolve against the data root rather than the project: a relative whitelist entry that pointed at a directory inside the code needs an absolute path, or moving.

  **A new site root layout**, which `basil --init` creates: `site.git/`, `releases/<commit>/`, a `current` symlink naming the active release, and `data/`. Point Basil at it with `basil --site /srv/mysite`, or run it from inside the site root. `basil.yaml` ships inside the release, so config is versioned and rolls back with the code. **The legacy single-directory layout is unchanged**: a plain project directory with a `basil.yaml` in it keeps working exactly as before, with the data root defaulting to the project directory, so `basil --dev` in a working copy needs no ceremony.

  **New key `data_dir`** — the data root. Defaults to `<site root>/data`, or the project directory in the legacy layout.

- **A public server refuses to start without `server.host`** — `hostPolicy()` returned `nil` when the host was empty, which told `autocert` to attempt issuance for *any* hostname a stranger put in SNI: a way to burn the site's Let's Encrypt rate limit from outside. Configuration validation now refuses, naming the fix, and the policy itself refuses every request rather than returning `nil`. `--dev` and a manually configured `https.cert`/`https.key` are the exceptions.

- **`basil --init` creates a site, not a project directory** — it now requires `--host` and `--admin`, and produces the site-root layout with the starter site **committed to the release branch and deployed as release 1**. Without an initial release a fresh server has nothing to serve, so it cannot answer an ACME challenge, cannot obtain a certificate, cannot be cloned over HTTPS, and can never receive the push that would give it a release. `--admin` is never derived from `$USER` or `$SUDO_USER` — `--init` runs on a server, where the shell is usually `root` — and is prompted for when a terminal is attached. It also creates the first admin account, prints its API key once, installs a pre-commit formatting hook, prints the exact clone command with the hostname and account name already in it, and, when run as uid 0, chowns the tree to `$SUDO_USER` (or warns and prints the exact `chown` command). The generated `.gitignore` is now three lines: runtime state is no longer inside the repository at all, so there is nothing to ignore (superseding the `certs/` and `cache/` entries added earlier in this release). Deploying, the Git hub itself and `basil publish` remain FEAT-153/154/155.

- **User-defined functions now enforce arity (BUG-032)** — calling an `fn` with the wrong number of arguments is an error, in both directions, reported at the call site: `add(1, 2, 3)` no longer silently discards the `3`, and `one()` no longer fails later with an `Identifier not found` pointing inside the function body (sometimes with a "Did you mean" hint naming another parameter). Both now raise `ARITY-0007` — "`add` expects 2 arguments, got 3" — with the caret on the call. This makes user functions consistent with builtins, methods, and loop callbacks, which have always been strict. Parsley has no varargs, so dropping extra arguments bought nothing.

  Internal callback dispatch adapts to the callee rather than passing a fixed count, so existing code keeps working: a prop-less component declared `fn()` still renders as `<C/>` (the props dict is passed only when the component declares a parameter for it), `.reduce` accepts both `fn(acc, elem)` and `fn(acc)`, and `.replace` is handed exactly as many arguments as it declares. The one-argument sites (`.map`, `.filter`, `.sort`, table `.where`/`.map`/`.find`/`.any`/`.all`/`.groupBy`, `mdDoc.walk`/`.map`/`.filter`) now say so with `ARITY-0008` — "Function passed to `map` must take 1 parameter, got 2" — instead of dropping the extra parameter.

  The Basil server's two dispatch sites adapt the same way: a Part view and an API handler are handed the props dict / request object only when they declare a parameter for it.

  **What to change:** any call passing extra arguments was a latent bug in the caller — remove them. For an optional value, use `??` in the body (`let x = arg ?? "default"`); default parameter values remain unimplemented. Destructuring parameters are unaffected: `fn({a, b})` is one parameter, and its missing keys still bind to `null`.

### Fixed
- **The first push to a fresh site now works with no manual Git configuration (BUG-033, closed)** — the documented clone/edit/push workflow failed on a fresh install: the served repository was the live site directory (a non-bare repo with a checked-out working tree), and Git refuses by default to accept a push into the checked-out branch, so the very first push was rejected with `! [remote rejected] … (branch is currently checked out)`. FEAT-154 removes the whole class of problem by serving a **bare** repository, so a push never contends with a working tree — no `receive.denyCurrentBranch`, no drifted-tree failure, no manual `git init`. A freshly initialised site accepts its first push out of the box, guarded by the regression test `TestGitE2E_BUG033_FreshSiteAcceptsFirstPush` (`server/git_e2e_test.go`). The phase-0 documentation fix and the `cache/` `.gitignore` entry recorded earlier in this release are superseded: the new `--init` keeps no runtime state inside the repository at all.
- **`server.host` is the public hostname, not a bind address (FEAT-152 review)** — the listener used `server.host`, which FEAT-152 made mandatory and had `basil --init` fill with a public FQDN. A site created that way could not start until DNS resolved, and could never start on NAT, Docker, or behind a load balancer, where the hostname is not an address the machine owns. `server.host` is now used only where a hostname belongs — the certificate, the WebAuthn relying-party id, printed URLs — and the listener uses the **new optional key `server.bind`**, empty by default, meaning all interfaces (which is what the port-80 ACME listener has always done). `--dev` still binds `localhost` when `bind` is empty.
- **`<data_dir>/uploads` is writable by site code with no configuration** — the directory was created by `--init`, advertised as `basil.uploads_dir` and served at `/__uploads/`, but every write to it was refused: `security.allow_write` was empty in the generated config. Uploads are a convention, not a setting, so the directory is now always in the write policy. Extra `allow_write` entries are unaffected.
- **The clone command `--init` prints now works** — the generated `basil.yaml` had no `git:` block and `git.enabled` defaults to false, so the very first instruction after `--init` returned 404. The generated config enables the Git server with `require_auth: true`.
- **`/__uploads/` no longer follows symlinks out of the uploads directory** — the handler was built on `http.Dir`, which blocks `..` but follows links, and uploads sits one level below the auth database and the certificate cache; a link planted there (by `rsync -l`, `tar -x`, `unzip`) made the handler an arbitrary-file reader. It is now opened as an `os.Root`, which refuses any component that escapes the root.
- **`/__uploads/` honours `auth.protected_paths`, and is not retro-published** — the route was registered raw on the mux, so a site protecting everything with `protected_paths: ["/"]` still served it to anonymous requests. It now goes through the same auth wrapping as any other route. It is also only registered for a site root created by `basil --init`: a legacy project with an existing `uploads/` directory (the old advice was to whitelist `./uploads`) is no longer published to the internet on upgrade. The docs now say plainly that the directory is world-readable over HTTP.
- **The data root is private (0700), and so are the auth database's SQLite sidecars** — the data root was created 0755 by both `--init` and the server, and SQLite creates `.basil-auth.db-wal` / `-shm` 0644. The `-wal` file holds uncheckpointed pages of the auth database — user rows, emails, the bcrypt hashes of deploy API keys — for the whole life of the running server, readable by every local account on a shared host. The database was already 0600; its sidecars now are too.
- **`basil --init` validates `--host` before it does anything** — the hostname was interpolated into `basil.yaml` as an unquoted scalar, so `--host '*.example.com'` produced a config that could not be parsed, and a hostname containing a newline injected arbitrary top-level keys. Because the API key is printed once and `--init` refuses to re-enter a non-empty directory, an unloadable config cost the operator the credential and the whole tree. The host is now checked (hostname or IP literal) before anything is created, written quoted, and the generated config is loaded and validated before the admin account is created.
- **A failed `basil --init` cleans up after itself** — a failure part-way through left a half-built site root, and the next attempt failed with "folder is not empty", which points at the wrong problem. Whatever `--init` created is now removed on failure; an empty directory the operator made themselves is emptied, not deleted. Run as root, `--init` also refuses a target that already exists or whose parent is writable by other accounts without the sticky bit — it makes several `git` calls between the emptiness check and the last write, and all of those writes follow symlinks.
- **The startup certificate probe backs off** — the eager ACME request fired on every start with no memory of failure, so a server under `Restart=always` with broken DNS or a blocked port 80 could burn Let's Encrypt's 5-failures-per-hour budget in seconds. A certificate already in the cache is now recognised and nothing is asked; a failure is recorded in the data root and suppresses the next attempt for 15 minutes, logging the same DNS/port-80 diagnosis from the marker instead of re-asking.
- **The `current` symlink is resolved once** — `ConfigPathForSite` and `ResolveAnchors` each followed it independently, so a deploy landing between the two could pair one release's `basil.yaml` with another release's files. The link is followed once, and the release path it names is what gets loaded.
- **A developer profile's `logging.output` is anchored** — it was the one configured path that still reached the config un-anchored, resolving against the operator's working directory. It is now anchored to the data root like the top-level key, and the path-anchor table test covers the three developer-profile overrides.
- **The Git deploy guide described a workflow that doesn't work (BUG-033, partial)** — `docs/guide/git.md` claimed "the `go-git-http` handler writes files to the site directory". It doesn't: it runs `git receive-pack`, which stores objects and updates refs. The working tree only changes if receive behaviour is configured to do it, and Basil never configures it — so on a fresh project the documented clone/edit/push workflow fails on the first push with `! [remote rejected] main -> main (branch is currently checked out)`. The guide now explains what actually happens, documents the manual `git init` and `git config receive.denyCurrentBranch updateInstead` needed on the server to use the feature today, and covers the follow-on failure where a push is refused (`Working directory has unstaged changes`) once the live tree has uncommitted changes to tracked files. A note points at `work/design/DESIGN-git-deploy.md`: the structural fix — pushing to a separate bare repository so a push never contends with a checked-out branch — is owned by FEAT-154, and no repository-creation or receive-configuration code is added here because that phase replaces it. The guide's user and API-key commands are also corrected to the ones the CLI actually implements (`basil users create --name/--email/--role` and `basil apikey create --user usr_… --name …`, plus `apikey list --user`, `apikey revoke key_…` and `users show usr_…`, all of which take IDs rather than names); the Quick Start and Configuration Reference YAML now include the `auth.enabled: true` that `git.require_auth: true` requires, without which the server exits at startup rather than merely rejecting a push; and example API keys use the real `bsl_live_` prefix instead of `bsk_`. Docs only; no behaviour change.
- **`basil --init` now gitignores `cache/`** — the default transformed-image cache (`images.cache_dir`, `./cache/images`) sat in a tracked path, so a site with image transforms would accumulate uncommitted changes to tracked files — precisely the drift that makes a Git deploy start getting rejected.
- **Undefined component errors now point at the tag and hint at imports (BUG-010)** — using a component that isn't in scope (e.g. `<Page>` without its import) previously reported "Undefined component" with no source position at top level, or with the position of the *calling* expression when used inside a function. The error now carries the component tag's own line and column, shows the offending line, and adds a hint: "Is `Page` imported? Check the import path and the exported name". (Long-truncated request values on server error pages also no longer split multi-byte characters.)
- **`variables.md` closure examples actually run now** — both closure examples reassigned a `let` binding from inside the closure (`let count = 0` + `count = count + 1`), which has errored with ASSIGN-0001 since immutability was enforced; they now declare with `var`. The dictionary-destructuring examples in the manual and reference also redeclared `name` across two `let` patterns and are updated for the new one-declaration-per-scope rule.
- **Array literal at the start of a line is no longer parsed as an index (BUG-031)** — a newline didn't end an expression, so `[1, 2]` on the line after a statement was read as indexing the previous expression: multi-element literals died with a confusing `expected ']', got ','`, and single-element ones (`[0]`) silently became an index, changing the program's meaning. An index/slice bracket must now open on the same line as the expression it indexes; a `[` starting a new line always begins an array literal. **Behaviour change:** code that deliberately split `expr` and `[index]` across lines (none found in this repo or its examples) must move the bracket back onto the expression's line.
- **`record.isValid()` no longer lies to `if` (BUG-030)** — Boolean truthiness depended on pointer identity with the interpreter's shared `true`/`false` singletons, so a `false` produced by `record.isValid()` (and several other internally-allocated Booleans, e.g. `response.ok`, file `isDir`/`isFile`) printed as `false` and compared `== false` correctly but was *truthy* in `if`/`!`/`&&`/`||` — meaning `if (record.isValid()) { save(record) }` saved records that failed validation. Truthiness now follows the Boolean's value, and all internal Boolean allocations use the shared singletons.
- **Unicode audit of string operations (BUG-029 follow-up)** — Audited every string method and every place other types consume strings for rune-correctness. String methods, indexing, slicing, `for … in`, natural sort, and the box renderer were already Unicode-aware; four byte-counting stragglers are fixed: schema `min`/`max` string-length validation now counts characters, not bytes (matching the "must be at least *n* characters" messages, the `minlength`/`maxlength` form attributes, and the generated SQL `char_length()` CHECK constraints — `"café"` is now length 4, not 5); `"x".truncate(n)` with a negative `n` no longer crashes the interpreter (it clamps to `0` and returns `""`); and display truncation in the REPL, `dev.log`, lexer error messages, and `mdDoc` titles no longer splits a multi-byte character mid-sequence.

### Added
- **`basil publish` — publishing gets its own verb (FEAT-155)** — `git push` shares work with the team; `basil publish` puts it in front of the public, so the command you type twenty times a day is the harmless one and going live is something you choose. Run inside a clone, it reads the release branch from the checked-out `basil.yaml`, shows the commit range and changed files about to go out and the drift the push closes, then asks before it moves anything — an empty line, or anything but `y`, cancels and pushes nothing. The server's deploy pipeline streams back as `remote:` lines while the push is still open; it reports the deployed commit on success, relays the `file:line:col` reason on a rejection, and exits non-zero when a release is refused. `--dry-run` prints the same plan and stops without pushing; `--yes` skips the confirmation for scripts. It needs no setup beyond the clone — it configures the release refspec on first use — and **no `basil.yaml` changes at all**. Underneath it is a plain push of the release branch, so raw `git push` and editor Git panels stay a working alternative; the verb is ergonomics, not a new protocol. A dirty working tree warns and proceeds, publishing the committed state. Documented in the rewritten [Git guide](docs/guide/git.md).
- **`basil fmt` — the Parsley formatter, built into the `basil` binary** — the same formatting engine as `pars fmt`, sharing `pkg/parsley/format` directly rather than shelling out, so a Basil install needs no `pars` binary on the machine. `-w` rewrites files in place, `-l` lists the files whose formatting differs and exits non-zero (usable as a CI gate), `-d` shows the diff without touching anything. Unlike `pars fmt`, arguments may be directories, which are walked for `*.pars` files (skipping `.git`); with no argument the current tree is formatted, so `basil fmt -w .` cleans a whole site and a bare `basil fmt` defaults to `-l` over the tree. A file that will not parse is reported as `file:line:col` and left untouched, one bad file never aborting a whole-tree run.
- **Drift reporting — the live site says when it has fallen behind** — the price of splitting sharing from publishing is that the live site can quietly lag the release branch, so Basil surfaces the gap rather than leaving it to be discovered. `basil status` reports what is live, what the release branch points at, and how many commits apart they are, naming the configured branch and printing the `basil deploy` that closes the gap; `basil publish` shows the same drift in its pre-confirmation summary; and `basil --dev` prints a one-line note at startup when the release branch is ahead of the live release. Drift degrades gracefully — a warning, never a failure — when origin is unreachable, falling back to the clone's last known remote-tracking state.
- **A Git hub: the server holds a bare repository, and a push publishes (FEAT-154)** — the Git endpoint at `/.git` is no longer the live site directory served over HTTP; it is a proper **bare repository** at `<site root>/site.git` that a team shares. A push into a bare repository never contends with a checked-out working tree, which is where [BUG-033](work/bugs/BUG-033.md) is structurally fixed — a fresh `basil --init` site accepts its first push with no manual Git configuration, and a clone of it yields the starter site (committed on the release branch by `--init`) rather than an empty repository. The endpoint is on whenever `site.git` exists — there is no `git.enabled: true` to write; `git.enabled: false` remains only as an off-switch. `git push` **shares** work with the team and publishes nothing; **publishing is moving the release branch**, which triggers the FEAT-153 deploy engine to check the release and, only if it passes, make it live. A push that moves any other ref is stored and does nothing else. The transport is now spoken by Basil directly — two endpoints over Smart HTTP — rather than through the `go-git-http` library, so the authenticated account name reaches the receive hooks per request and concurrent pushes each record their own publisher. Documented in the rewritten [Git guide](docs/guide/git.md); the deploy pipeline it triggers is the [Deployment guide](docs/guide/deployment.md).
- **Real receive hooks — a push is checked before it becomes the site** — deploys are driven by genuine Git hooks, not a library callback fired after the fact. A `pre-receive` hook validates the release branch **before** any ref moves: validation failure exits non-zero, the push is rejected, the ref does not move, and the live site is untouched — with the reason (`file:line:col: message`) relayed to the developer's terminal as `remote:` lines while the push is still running. A `post-receive` hook then activates the release through the engine. Both hooks are thin scripts calling `basil deploy --from-hook` — no deploy logic lives in shell — and Basil installs them, re-installing on startup if they are missing so a repository cannot silently stop deploying.
- **`deploy.branch` names the release branch (default `live`)** — the branch a push must move to publish. The default keeps sharing (`git push`) and publishing (a push to `live`) separate; setting `deploy.branch: main` restores push-to-publish for anyone who wants a commit to go live the moment it is pushed. The implementation speaks in refs, so a **tag** is accepted as a release ref (`refs/tags/…`) even though configuration and docs speak in branches. — deploying is now a thing Basil *does* rather than a side effect of files appearing on disk. `basil deploy <sha|branch|tag>` takes a commit already in the site's repository and runs one pipeline: resolve, lock (one deploy at a time per site), materialise into `releases/<commit>/` byte-identical to the commit, validate, activate, hook, record, prune. Every `.pars` file is parsed and the release's `basil.yaml` loaded and validated *before* activation — Basil owns the Parsley parser, so it can read a release and decline it — and a release that fails is rejected with grep-able `file:line:col` errors, its directory removed, **the live site unchanged**. Validation catches code that is broken, not work that is unfinished, and has no config key to disable it; `basil deploy --no-validate` is the emergency override, needing shell access, which is the right bar for skipping a safety check. Activation atomically re-points `current`; a running server notices through its own watcher on the site root and rebuilds routes and caches against the new release while requests in flight complete on the one they started on (listener settings — `server.port`, `server.bind`, `server.host`, `https.*` — cannot be re-bound live and log a restart-required warning; middleware, subsystem and `images.*` settings also wait for a restart). Deploying with the server stopped activates the release for its next start. Documented in the new [Deployment guide](docs/guide/deployment.md).
- **Five deploy subcommands** — `basil deploy <sha|branch|tag>` runs the pipeline; `basil rollback [id]` re-activates the previous release, or one named by sequence number or SHA prefix — a symlink swap and cache clear, never a re-materialise, so a pruned release is refused with the `basil deploy <sha>` that rebuilds it; `basil releases` shows the deploy record, newest first, with the live release starred and rejection reasons inline; `basil status` says what is live and whether the release branch is ahead of it; `basil check` verifies the bootstrap preconditions — layout, active release, repository present and *not* resolving inside a served root, `server.host`, DNS, port 80, certificate — each reported plainly with a fix hint. All five take `--site`/`--config` and exit non-zero on failure.
- **The deploy record** — SQLite at `<data_dir>/deploy.db`, readable with or without the server running, written for every outcome: `deployed`, `rejected`, `failed`, `no-op` (deploying the already-live commit) and `rolled-back`. Each entry stores commit, timestamp, duration, trigger and **both identities** — the publisher who triggered the deploy (`cli:<os user>` from the CLI) and the commit author read from the commit itself. They routinely differ (someone merges and publishes a colleague's work), and storing only one would make the record useless for the question it did not store.
- **`deploy.keep`** — the one setting deployment adds: how many release directories to retain (default 5). Pruning runs after each successful deploy, never removes the active release, and a value of 0 or less disables it. The record keeps every entry; only directories are pruned.
- **`deploy.pars` post-deploy hook** — a Parsley script in the release root (next to `basil.yaml`) runs after activation. Convention, not configuration, like `index.pars`: its presence is the whole setting. A hook failure is recorded and reported loudly but never rolls the deploy back — a migration that half-ran is not made better by reverting the code underneath it. Hooks should write through absolute paths (ideally under the data directory): a relative `@./` path lands inside the release, which pruning will eventually delete.
- **`basil --site PATH`** — point Basil at a site root; the config is read from the active release through `current`.
- **A durable place for site code to write** — `basil.data_dir`, `basil.uploads_dir` and `basil.uploads_url` are available to handlers, and `<data_dir>/uploads` is served at `/__uploads/` in the site-root layout, following the existing `/__p/` and `/__img/` pattern. Uploads no longer have to live inside `public_dir`, where the next deploy would delete them. The directory is always writable by site code, with no `security.allow_write` entry. Directory listings are not served, symlinks that leave the directory are refused, and everything in it is public over HTTP unless `auth.protected_paths` says otherwise.
- **The certificate is obtained at startup, not on the first handshake** — `autocert` issues lazily, which made the developer's first `git clone` the request that triggered issuance; when ACME failed, the handshake failed and Git reported an opaque TLS error. Basil now asks for the certificate as soon as the port-80 listener is up and logs the outcome, naming DNS and port 80 when it fails. A failure is logged, not fatal: the server keeps running and retries on the first HTTPS request.
- **Search indexes are written to the data root** — an `@SEARCH` index with a relative path (or an auto-named one) landed inside the handler tree, so every deploy destroyed it. Indexes now go to `<data_dir>/search/`. `pars`, which has no data root and no deploy, keeps the old script-relative behaviour.
- **CSRF failures use the standard 403 page** — A failed CSRF check in production wrote a bare `403 Forbidden` string and never consulted `error_pages`, so it looked nothing like a role failure on the same site. It now renders the same 403 page (custom page included), and API callers get `{"error": {"code": "HTTP-403", "message": "Forbidden: CSRF token validation failed"}}` instead of HTML. Dev mode keeps its detailed diagnostic naming which of the two tokens went missing — as HTML for a browser, and in the JSON `details` field for a `fetch()` caller.
- **API requests get JSON errors, and 403s get a real page** — A 404 or 500 for a request that looks like an API call (`Accept: application/json`, a JSON `Content-Type`, or a path under `/api/`) now returns `{"error": {"code": "HTTP-404", "message": "Not Found"}}` instead of a 4.7KB HTML error page; dev mode adds a `details` field with the underlying error, production keeps details in the logs. Role-gated paths previously answered a browser with plain-text `403 Forbidden`; they now render a built-in 403 page (overridable via `error_pages`, like 404/500), while API clients keep the existing `"Forbidden: insufficient role"` JSON. Content negotiation runs before error pages, so a custom HTML template is never served to a JSON client.
- **Final 404/500 error pages, and custom pages via `error_pages` config** — The placeholder gradient error pages are replaced with the designed ones: a centred face icon, "PAGE NOT FOUND" / "SERVER ERROR" title, and a back button (`history.back()` with a home-link fallback), in light and dark following the system theme, self-contained with inline SVGs. Sites can also replace them: `error_pages: {404: ./errors/404.pars}` in `basil.yaml` maps any error status code (400–599) to a Parsley template (backlog #45); a missing or broken custom page logs the problem and falls back to the built-in page.
- **`fetch` responses are size-bounded** — HTTP fetches now cap how much of a response body is read into memory (default 100 MB), so a large or hostile upstream can't exhaust memory. Override per request with `{maxSize: bytes}` on the format factory (e.g. `text(url("…"), {maxSize: 5_000_000})`); a non-positive value disables the cap. An over-size body is rejected with a clear error rather than silently truncated.
- **Runaway recursion is now a catchable error, not a crash** — The evaluator bounds function-call depth (`evaluator.MaxCallDepth`, default 5000) and returns a Parsley error (`CALL-0007`, "Maximum call depth exceeded") when a function recurses without a base case. Previously such a script would overflow the Go stack and take down the whole process; now it fails cleanly with a hint, and legitimate deep-but-bounded recursion is unaffected.
- **Panic-recovery middleware** — The Basil HTTP server now wraps every request in an outermost recovery layer, so an unexpected panic in a handler or middleware becomes a logged `500` (with the stack trace on stderr; full detail in the response only in dev mode) instead of a dropped connection. Streaming responses (SSE/live-reload) still work — the wrapper forwards flushing via `http.ResponseController`.
- **Protected paths and role-gated routes** — Sites can require authentication for parts of the app: signed-out visitors are redirected to the login page (`login_path`, default `/login`) and signed-in visitors without the right role get a 403. Works site-wide or per-route via `auth: required`, with `basil.auth.user.role` (`"admin"` / `"editor"`) and `basil.auth.required` available to templates.
- **`part-target` and `part-form` for Parts** — An element *outside* a Part can now update it: give the Part an `id` and trigger it from anywhere with `part-click`/`part-submit` via `part-target="id"`, adding `part-form="formId"` to send a named form's fields when the trigger isn't inside one.

### Changed
- **The pre-commit hook installed by `basil --init` now formats with `basil fmt` (FEAT-155)** — the hook `--init` writes into `.githooks/pre-commit` runs `basil fmt -w` on the staged `.pars` files and re-stages them, so committed code is formatted without anybody deciding anything. Formatting is fixed locally, before the commit exists, rather than gated on the server — a pre-commit hook keeps shared history clean with no setting to turn on, and nobody is ever refused by a server over whitespace. (Enable it in a fresh clone with `git config core.hooksPath .githooks`, which `--init` prints.)

The push was accepted.` as `remote:` lines — a separate, non-fatal channel that never touches the push's exit status. Formatting is style, not correctness, so it never blocks a release, and the server never rewrites code (it reports, it does not fix). - **Declaring a name twice in the same scope is now an error (`DECL-0001`)** — `let x = 1` followed by another `let x = ...` (or `var x = ...`) in the same scope silently rebound the variable, which made `let`'s immutability trivially bypassable: `x = 2` was an error but `let x = 2` did the same thing, and closures observed the new value (so it wasn't Rust-style shadowing, just reassignment through a back door). All declaration forms now enforce one-declaration-per-scope — plain `let`/`var`, array and dictionary destructuring (including `...rest` and `as` aliases), and the `fetch`/read/query binding forms — matching JavaScript's `let`/`const`, Swift, Go, and Kotlin. Shadowing in a genuinely *inner* scope (function body, `if` block) is still allowed, and the REPL retains redeclaration at the prompt for convenience (like browser consoles). Also fixed in passing: `var x` after `let x` used to leave the binding immutable while claiming otherwise; in the REPL, where redeclaration is allowed, it now genuinely converts the binding to mutable.
- **`if`/`else` blocks now have their own scope** — declarations inside a branch no longer leak out (`if c { let y = 1 }` used to define `y` for the rest of the program, contradicting the manual's own scoping section). Reading and assigning *outer* variables from inside a branch works as before; only declarations are contained. Code that relied on the leak should return the value from the block instead — `if` is an expression: `let y = if (c) { 1 } else { 0 }`. `for` bodies, `with` blocks, and function bodies already scoped correctly and are unchanged.
- **Enclosed scopes no longer rebuild `@env`/`@args`** — every function call, loop iteration, and (now) `if` branch creates an enclosed environment, and each one used to re-read and re-sort the entire process environment into a fresh `@env` dictionary that immediately shadowed the identical one in the root scope. ### Fixed
- **SFTP `rmdir({recursive: true})` now actually removes the tree** — The `recursive` option was parsed but silently ignored: `RemoveDirectory` only removes empty directories, so a recursive call on a non-empty directory failed (or misled). It now walks the remote tree depth-first, deleting contents before their parent directories, matching `os.RemoveAll` semantics. A plain non-recursive `rmdir()` on a non-empty directory still errors, as before.
- **String `[i]` indexing and `[a:b]` slicing are now rune-based, not byte-based (BUG-029)** — `.length()` and `for … in` iteration have always counted Unicode codepoints, but indexing and slicing counted bytes, so on non-ASCII text they could land in the middle of a multi-byte character and return an invalid partial byte (`"café"[3]` → `"Ã"` instead of `"é"`; `"café"[0:4]` split the `é`). Both paths in `evalStringIndexExpression`/`evalStringSliceExpression` now convert to `[]rune` first, so index/slice positions, negative indices, out-of-range (`INDEX-0001`) detection, optional access (`[?n]`), and beyond-length clamping are all measured in characters, consistent with `.length()`. **Behaviour change:** any code relying on byte indices into non-ASCII strings will now get character positions instead (`"café"[3]` → `"é"`, `"a中😀"[1]` → `"中"`); pure-ASCII strings are unaffected. The manual now documents the model too: a new **Text & Unicode** section on the Strings page states that `.length()`, `for … in` iteration, and `[i]`/`[a:b]` indexing/slicing are all character- (rune-) based, and the Control Flow page's string-iteration example shows a multi-byte case.

### Security
- **Git over plain HTTP is refused, not warned about (FEAT-154)** — HTTP Basic auth carries the API key in an easily-decoded header, so a plain-HTTP Git request is a plaintext credential with push rights on the wire. Where the old handler logged a warning and served anyway, the request is now refused with an error explaining why. The refusal is scoped to the Git endpoints: port 80 continues to answer ACME HTTP-01 challenges at `/.well-known/acme-challenge/` ahead of the HTTPS redirect, so certificate issuance and renewal are unaffected (tested explicitly, not assumed). The sole exception is a `--dev` localhost bind, decided in code and never from configuration.
- **A repository inside a served root refuses startup (FEAT-154)** — the repository path is fixed at `<site root>/site.git` and is not configurable, but `public_dir`, `site.path` and `static[].root` are; Basil refuses to start if the repository resolves inside any of them, since a repository under a served root would hand every version of every file to anyone with a browser.
- **No auth database, no Git (FEAT-154)** — a server with no auth database refuses Git entirely, promoted from an incidental check to a stated guarantee with a test. Authentication cannot be disabled from a config file (`git.require_auth` is gone); `--dev` on localhost is the only relaxation.
- **The release branch cannot be force-pushed or deleted (FEAT-154)** — by anyone, with no setting to permit it. A rewritable release history would make the deploy record, and therefore rollback, unreliable. Force-push and deletion of the release branch are both refused in `pre-receive`, with an error naming the reason; other branches are unaffected.

## [1.0.0-alpha.2] - 2026-07-12

### Added

#### Release & CI Infrastructure

#### Image Transformation (FEAT-148)
- **`image()` builtin** — Transform images and serve them at content-hashed, immutable URLs. Auto-rotates via EXIF, strips metadata, resizes (width/height/fit or center-crop), converts format, and caches results to disk. No upscaling; concurrent transforms are deduplicated via singleflight.
- **`imageInfo()` builtin** — Returns `{width, height, format, orientation}` for an image without transforming it. Results are cached in memory (keyed by path + modification time) for efficient gallery-page use.
- **`imageBlur()` builtin** — Generates a Low Quality Image Placeholder (LQIP) as an inline `data:image/jpeg;base64,...` URI (~600 bytes). Use as an instant CSS background while the full image loads.
- **`imageSrcset()` builtin** — Generates multiple resized variants and returns `{src, srcset, width, height}` for responsive `<img>` tags. Supports both width descriptor mode (`[400, 800, 1200]`) and density descriptor mode (`[1, 2, 3], "x"`).
- **WebP output encoding** — All four builtins support WebP output via `gen2brain/webp` (pure-Go, no CGo). Uses native `libwebp` when available on the host, with a WASM fallback (`wazero`) otherwise. WebP typically produces 67–72% smaller files than JPEG for photos.
- **Automatic sharpening on downscale** — A subtle unsharp mask (σ=0.5) is applied after resize to recover edge detail. Disable with `{sharpen: false}` or set an explicit sigma with `{sharpen: 1.2}`.
- **Disk cache at `/__img/`** — Transformed images are served at `/__img/{hash}.{ext}` with immutable `Cache-Control` headers. Cache is stored at `./cache/images/` by default (configurable via `images.cache_dir`).
- **Binary size note** — The `basil` binary grows by ~4 MB (35 MB → 39 MB) due to the bundled WASM runtime. Install `libwebp` on your production host (`brew install webp` / `apt install libwebp-dev`) to use the faster native encoder and confirm the runtime path at startup.

#### Content-Aware Image Operations (FEAT-149)
- **Smart crop** (`{crop: "smart"}`) — Analyses images for faces and high-interest regions (edges, saturation, skin tones, composition) and crops to preserve them. Uses a two-pass architecture: PICO face detection at 640px followed by heuristic scoring at 256px. Pure Go, no new dependencies — the PICO cascade file (234 KB, MIT-licensed) is embedded via `go:embed`.
- **Focal point option** (`{focal: {x, y}}`) — Guide smart crop toward a specific point or region using normalised (0–1) coordinates. Supports both point `{x, y}` and rectangle `{x, y, w, h}` forms.
- **Seam carving** (`{scale: "smart"}`) — Content-aware resizing that removes or inserts low-energy pixel paths (seams) instead of uniformly scaling. Preserves faces, text, and important content when changing aspect ratio. Supports both reduction and enlargement. Based on Avidan & Shamir, SIGGRAPH 2007.
- **Validation** — `crop: "smart"` requires both width and height; `focal` requires `crop: "smart"`; `crop` and `scale` are mutually exclusive. Changes beyond 30% via seam carving log a warning.

## [1.0.0-alpha.1] - 2026-02-26

**Parsley 1.0 Alpha** — The first alpha release of the Parsley programming language.

### Breaking Changes
- **`let`/`var` variable declarations** (FEAT-122) — Swift-style immutable/mutable semantics replace bare assignment. `let` for immutable bindings, `var` for mutable.
