# BUG-051: the other half of BUG-045

## Summary
`.short()`, `.medium()`, `.long()`, `.full()` and `.fmt()` printed a datetime as
a bare date, identical to the date-only value:

```parsley
@2024-12-25T14:30:00.medium()  // "Dec 25, 2024"
@2024-12-25.medium()           // "Dec 25, 2024"  — indistinguishable
```

A page showing an event's time showed only its day, and there was no way to get
a datetime's time through `.fmt()` at all.

## Cause
`formatDateWithStyleAndLocale` special-cased the two time kinds — BUG-045's fix
— and then fell through to date-only patterns for everything else. BUG-045
stopped at the two kinds it had a reported symptom for and wrote the datetime
case down as an open design question rather than a defect, on the grounds that
FEAT-146 had chosen the date portion deliberately for interpolation. It is a
defect: a renderer that drops half its input is not a style choice, and the
choice FEAT-146 actually made was about `{d}` in a template, not about what
`.full()` means.

## Decision
**Print the time to the precision the value carries, and none when it carries
none.** A datetime has one kind for three precisions, so its own content is the
only signal available:

```parsley
@2024-12-25T14:30:00.medium()    // "Dec 25, 2024, 14:30"
@2024-12-25T14:30:45.medium()    // "Dec 25, 2024, 14:30:45"
@2024-12-25T00:00:00.medium()    // "Dec 25, 2024"
datetime("2024-12-25").medium()  // "Dec 25, 2024"
```

That mirrors the `time` / `time_seconds` split above it in the same function.
The midnight case earns its exception: `datetime("2024-12-25")`, a database date
column and a JSON date all widen a date into a datetime at exact midnight, so an
unconditional rule would hang `", 00:00"` off most dates on most pages. Nothing
is lost either way — a value at midnight prints what a person would write for
it, and one carrying seconds keeps them.

Two smaller decisions inside it:

- **The connector is a comma, in every locale and every style.** English "at"
  reads better in `long` and `full`, but then every locale needs its own word,
  and thirty guessed translations are worse than the comma nearly all of them
  already use for the shorter styles.
- **The time is 24-hour and locale-independent**, matching `.time`,
  `datetimeDictToString`, and BUG-045's rendering of the time kinds. Whether
  `en-US` should get `"2:30 PM"` is still a separate, open question — it now
  applies to all three time-bearing kinds at once, which is the right shape for
  it.

`{format: "date"}` on a record column is unaffected: it asked for a date, so it
still gets the date portion, the same as the ISO-string branch beside it. That
call now goes through `formatDatePortionWithStyleAndLocale` so the intent is
written down rather than inherited from a bug.

## Docs
The 2026-08-29 audit had changed six sites in `builtins/datetime.md` to match
the buggy output, with a note to revert if the time was meant to be there. They
are reverted, and the `fmt()` section now states the rule and its midnight case
outright.

## Verification
`TestStyledDatetimeCarriesItsTime` covers all four styles, `.fmt()` with a style
and with an options dictionary, template interpolation, seconds, midnight from
both a literal and `datetime()`, two locales, and the three neighbouring kinds
that must not move. `TestFormatRespectsKind` and
`TestDatetimeTemplateInterpolationMedium` each had a case pinning the dropped
time as correct; both are updated in place with a note saying so.
