# BUG-043: the dev watcher did not know about `.part`

## Summary
`basil --dev` watches handler files and clears the module cache when one
changes. Its extension switch listed `.pars` and `.parsley` and nothing else, so
an edited `.part` file invalidated nothing: the page kept rendering the version
that was on disk when the server started.

Yes, it was cached — in `evaluator`'s module cache, which nothing was clearing.

## Why it took a while to see
A Part is reachable two ways, and only one of them was stale:

- **Its own endpoint** (`GET /shows.part?_view=default`, what `part-refresh`
  polls) re-reads the file, so polling showed the **new** version.
- **The copy rendered into the page** by `<Part src={…}/>` comes from
  `importModule`, so it showed the **old** one.

Reproduced with a Part whose body said `VERSION-ONE`, edited to `VERSION-TWO`
with the server running:

| Source | Showed |
| --- | --- |
| the file on disk | `VERSION-TWO` |
| `GET /shows.part?_view=default` | `VERSION-TWO` |
| the index page's server-side render | `VERSION-ONE` |

With `part-refresh={1000}` the page therefore loaded stale and corrected itself
a second later, which reads as a flicker rather than a cache. Without a refresh
interval it would simply have stayed wrong until restart. Neither did the
browser live-reload on the edit: `shouldTriggerReload` used the same incomplete
list, so saving a `.part` did nothing at all.

HTTP caching was ruled out on the way: Part responses already carry
`Cache-Control: no-cache, no-store, must-revalidate`.

## Fix
`.part` joins `.pars` and `.parsley` — but as a single shared list rather than a
third entry in two switches:

```go
func isModuleExtension(ext string) bool {
	switch ext {
	case ".pars", ".parsley", ".part":
```

Both `shouldTriggerReload` and `handleFileChange` consult it, because a type
that reloads the browser but does not clear the cache — or the reverse — is
precisely the shape this bug took, and two hand-maintained lists will drift
again.

`.pln` was checked and is not affected: it is a data format read through
`readFileContent`, not imported as a module, so it never enters the cache.

## Verification
- End to end with the built binary: with the server running and a Part edited in
  place, the index page went from `VERSION-ALPHA` to `VERSION-BETA` with no
  restart, and the watcher logged `handler changed: shows.part`.
- `TestWatcher_HandlesPartFiles` pins `.part` in both roles and pins the
  exclusions (`.db`, `.txt`) that stop a dev server reloading the browser in a
  loop over its own log database.

## Notes
`InvalidateModule` ignores its argument in the end — the targeted deletes are
followed by `moduleCache.modules = make(...)`, clearing everything, under a TODO
about tracking import dependencies. That is why an editor that saves through a
temporary file (`sed -i`, and vim by default) still worked once `.part` was
watched: the event named `.!70733!shows.part`, which matched no cache key, but
the blanket clear covered it. Worth knowing before anyone implements the TODO —
selective invalidation would make temp-file saves stop working unless the rename
event is what gets handled.
