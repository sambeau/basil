# BUG-038: publish suppressed the very gitconfig holding the operator's credential

## Summary
`basil publish` ran every git subprocess with `GIT_CONFIG_NOSYSTEM=1`. On macOS the
osxkeychain credential helper is configured in the **system** gitconfig that Xcode
ships, so that variable took the operator's stored API key away from git. Publish
could not reach the remote at all — while the operator's own `git push` to the same
remote, in the same clone, worked perfectly.

```
$ git config --show-origin --get-all credential.helper
file:/Applications/Xcode.app/Contents/Developer/usr/share/git-core/gitconfig	osxkeychain
```

Isolated cleanly: `GIT_TERMINAL_PROMPT=0` alone exits 0, `GIT_CONFIG_NOSYSTEM=1`
alone exits 128.

## Symptoms
The first symptom was cosmetic and misleading — the drift check degraded to a
warning and publish carried on:

```
warning: could not reach origin to check drift (git ls-remote --symref origin HEAD:
exit status 128); using the last known state from this clone
```

But the *push* used the same environment (`streamGit`, `publish.go`), so an actual
publish — as opposed to a no-op — would have died with:

```
fatal: could not read Password for 'https://sam@host': terminal prompts disabled
```

Every macOS operator would have hit this on their first real `basil publish`. The
quick path (`git push` straight to the release branch from a clone of the server)
was never affected, which is what hid it: the bug only shows up in the deliberate
workflow the docs recommend.

## Cause
`runGit` and `gitOutput` (`cmd/basil/init.go`) set `GIT_CONFIG_NOSYSTEM=1`, and
publish reused them along with its own `streamGit`. For the rest of the CLI that is
correct — those calls only ever touch a local repository, and keeping a machine's
system gitconfig out of Basil's own bookkeeping is worth something. Publish is the
one client-side command that contacts a remote, and credential helpers are routinely
configured in exactly the file the variable suppresses.

## Fix
Publish gets its own git runners — `clientGit`, `clientGitOutput` and the existing
`streamGit` — all sharing `clientGitEnv()`, which sets `GIT_TERMINAL_PROMPT=0` and
nothing else. Every git call in `publish.go` goes through them, so the rule is a
property of the file rather than a judgement at each call site: **publish is a
wrapper around the operator's git, so it reads the operator's git configuration,
all of it.** `runGit`/`gitOutput` are unchanged for `init.go` and `deploy.go`.

`clientGitEnv` deliberately does not force `GIT_CONFIG_NOSYSTEM=0`. An operator who
exports it has broken their own `git push` the same way; publish should fail
identically rather than second-guess the environment.

## Verification
- `TestClientGitEnv_ReadsTheOperatorsSystemGitconfig` asserts the variable is absent
  and `GIT_TERMINAL_PROMPT=0` present, and says why, so a later tidy-up toward
  consistency with `runGit` fails loudly.
- Confirmed against the live test site: with no local `credential.helper` override,
  `basil publish --dry-run` reaches origin and resolves the release branch. Before
  the fix the same command warned it could not reach origin.

## Notes
The workaround, for anyone on an older build: `git config credential.helper
osxkeychain` inside the clone. Local config is not suppressed by
`GIT_CONFIG_NOSYSTEM`.
