# BUG-045: two renderers, and interpolation was moved to the wrong one

## Summary
`formatDateWithStyleAndLocale` had a single code path — date patterns — for all
four datetime kinds. `kind` appeared nowhere in `eval_locale.go`. So a value
whose entire content is a time printed as a bare date:

```parsley
@timeNow            // "Aug 26, 2026"  — for 00:32:17
@14:30.fmt("full")  // "August 26, 2026"
```

Since FEAT-146 routed template interpolation through this renderer, `{t}`
printed a date too. There was no way to display a clock through `.fmt()` at all;
the `.time` property was the only route.

## How it got past the tests
Basil has **two** datetime renderers, and only one was kind-aware:

| Renderer | Used by | Kind-aware |
| --- | --- | --- |
| `datetimeDictToString` | ISO / table output | yes — switches on all four kinds |
| `formatDateWithStyleAndLocale` | `.fmt()`, `.medium()`, interpolation | no |

FEAT-146 moved template interpolation **from** the kind-aware renderer **to**
the kind-blind one. Its spec justified the move on a property the destination
did not have:

> DateTime `.medium()` respects kind: date-only → "Jun 15, 2025", full datetime
> → "Jun 15, 2025" (date portion)

> The original TODO noted `.medium()` didn't handle datetime kinds. Testing
> confirms it now works correctly for all kinds.

The confirmation was real but hollow. The test written for it,
`TestDatetimeTemplateInterpolationMedium`, has exactly two cases — a `date` and
a `datetime` — and those two kinds produce *identical* output here. Agreement
between them looked like kind-awareness and was in fact the absence of it. One
case is even named `full_datetime`, formats a value carrying `14:30:00`, and
asserts `"Dec 25, 2025"`: the suite did not merely miss the dropped time, it
pinned it as correct.

Neither time kind was formatted by any test in the repository. No test anywhere
called `.fmt("short"|"medium"|"long"|"full")` on a datetime at all.

## Fix
The styled renderer switches on kind, the same way `datetimeDictToString`
already did:

- `time` → `"14:30"`
- `time_seconds` → `"14:30:45"`
- `date`, `datetime` → unchanged

24-hour and locale-independent, matching the `.time` property and
`datetimeDictToString`. Whether `en-US` should get `"2:30 PM"` is a separate
question from whether a time should print as a date, and is not answered here.

**`datetime` deliberately keeps FEAT-146's behaviour** of rendering its date
portion. That was a considered decision about human-facing output, it is
documented, and sites depend on it. Whether `.fmt("full")` on a datetime ought
to include the time is a design question, not a defect, and is left open.

## Verification
`TestFormatRespectsKind` covers all four kinds through `.fmt()`, the `.medium()`
sugar, and template interpolation — including the two cases that must *not*
change, so a future kind-awareness change cannot quietly move `date` or
`datetime` either.

## Notes
`@timeNow` has kind `time`, so it renders `"01:01"` — no seconds — while its
`.time` property returns `"01:01:42"`. A clock that ticks by the second still
wants `.time`. Whether `@timeNow` should be `time_seconds` is worth a look.
