# BUG-028: Non-ASCII mangled in `<script>`/`<style>` raw text

## Summary
Multi-byte UTF-8 characters inside `<script>` and `<style>` tag contents are
corrupted: the first byte of the sequence survives but the continuation bytes
are dropped. The raw-text scanner appears to iterate bytes rather than runes.

## Reproduction
```parsley
<script>var x = "☾ moon";</script>
```
Output bytes: `22 e2 20 6d ...` — the `☾` (`e2 98 be`) is emitted as a lone
`e2` byte (invalid UTF-8, renders as `�`). Same for `<style>`:

```parsley
<style>.a::before { content: "☾"; }</style>
// renders: .a::before { content: "�"; }
```

Regular Parsley strings and tag text handle the same characters correctly —
only the raw-text mode used for script/style contents is affected.

## Expected
Raw text should pass UTF-8 through byte-for-byte (minus `@{}` interpolation
handling).

## Suspected Location
The lexer's raw-content scanning for script/style tags (pkg/parsley/lexer) —
likely advancing one byte at a time and appending only ASCII-range bytes, or
casting bytes through rune incorrectly.

## Resolution
Fixed in `pkg/parsley/lexer/lexer.go`. `readChar()` advances by the full
UTF-8 rune width but stores only the rune's *first byte* in `l.ch`; the
content scanners appended `l.ch` directly, so continuation bytes were
dropped. Switched three scanning loops to the existing `appendCurrentChar()`
helper (which copies all bytes of the current rune):

- `readRawTagText()` — the script/style raw-text scanner (the reported bug)
- `readTagText()` — plain tag text scanner (same latent pattern)
- `readCDATA()` — CDATA section contents (same latent pattern)

`@{}` interpolation inside raw text is unaffected and still works alongside
multi-byte characters.

Tests: `TestUnicodeInRawTextTags` in `pkg/parsley/lexer/unicode_test.go`
(token-level) and `pkg/parsley/tests/raw_text_unicode_test.go` (end-to-end
eval, including interpolation mixed with multi-byte glyphs).

The workaround in `site/components.pars` (JS `\u2600`/`\u263E` escapes for
the theme-toggle glyphs) has been reverted to real `☀`/`☾` characters.

## Workaround
~~Use escape sequences in the embedded language: `"\u263E"` in JS,
`"\263E"` in CSS.~~ No longer needed.

Building the site's theme toggle (site/components.pars) — the ☀/☾ glyphs in
