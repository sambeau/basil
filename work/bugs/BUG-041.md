# BUG-041: a precise position in the wrong file

## Summary
An error raised inside an imported component carried a line and column but no
file. The server filled the gap with the handler it happened to be serving
(`handleStructuredError`, `server/handler.go`), so the error was reported
against the page that *used* the component, at the component's line number.

The result is worse than having no position at all: the error page names a file
and highlights a line, confidently, and both are wrong. Reproduced with an
undefined `<Zzz/>` at line 5 column 7 of `components/page/page.pars`:

```
site / index.pars    5 : 7
```

with the code window showing `index.pars` line 5 — `<div class="photo-wrap">`,
entirely innocent. The reporter hit this chasing BUG-040 and spent the search
staring at a `<header>` tag in a file that was fine.

## Cause
`Error` has carried a `File` field all along, and most of the evaluator sets it
from `env.Filename` — an undefined *identifier* inside a component was already
attributed correctly. Tag and component evaluation was the gap:
`newUndefinedComponentError` took only a name and a token, and every positioned
`&Error{...}` literal in `eval_tags.go` set `Line` and `Column` without `File`.

That is exactly the code that runs inside components, so the one part of the
evaluator that could not name its own file was the part most likely to be
executing in a file other than the handler.

## Fix
`newUndefinedComponentError` takes the source file and stores it, and all 13
positioned error literals in `eval_tags.go` — Part resolution, cache directives,
form context, the null-component check — now carry `File: env.Filename`. Nothing
downstream needed touching: `createErrorEnv` already parses the file out of the
message and feeds `getSourceContext`, so both the displayed path and the code
excerpt correct themselves.

Verified against the same reproduction: `components / page / page.pars  5 : 7`,
with the highlighted line reading `<Zzz/>`.

## Verification
- `TestComponentError_NamesTheFileItIsIn` builds a two-line page importing a
  component whose fault is on line 3, so a line number attributed to the wrong
  file is checkably wrong rather than coincidentally plausible.
- A mechanical sweep of `eval_tags.go` for `&Error{}` literals that set a
  position without a file now reports none.

## Notes
The sweep was scoped to `eval_tags.go`, the file this bug was found in. Other
evaluator files may hold positioned errors without a file; the ones exercised
here (identifiers, infix, tables, form binding) already set it. A repository-wide
audit is worth doing if another misattribution turns up, but was not done
speculatively.
