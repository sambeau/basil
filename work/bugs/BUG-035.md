# BUG-035: a release could publish the site's repository by moving a served root

## Summary
`checkRepoOutsideServedRoots` refuses to serve Git when the bare repository sits inside
anything the server serves files from. It ran **once**, in `initGit`, against the config
the process started with. Nothing re-ran it when a deploy activated a new release.

The served roots are release-owned, and rightly so — serving files is what a release is
*for*. `static[].root`, `public_dir`, `site.path` and `routes[].public_dir` all resolve
against the release directory, none of them had any containment validation, and
`static` is not on `carryRestartRequiredSettings`' list, so a release's value takes
effect at the next `SwapRelease`.

So a release carrying

```yaml
static:
  - path: /s/
    root: ../..
```

resolved that root to the **site root** and served it — `site.git` included — as
unauthenticated static files from the moment `current` moved. That is the whole
history: every branch never published, every secret ever committed, plus `data/` and
the auth and deploy databases in it. `site.git` does not begin with a dot, so the
dotfile filters do not cover it, and `basil.gitEnabled false` does not help either — a
static file handler does not consult the Git endpoint's switch.

The startup check could not catch it: by then it had run against a config two deploys
old. Only a restart would refuse the site — and a restart is exactly what a working
deploy avoids.

## Reproduction
`TestSwapReleaseRefusesReleaseThatServesTheRepository` (`server/activate_test.go`) is
the bug written down. With the guard removed it activates the release and
`GET /s/site.git/HEAD` returns `ref: refs/heads/main` — the repository, over plain HTTP,
to anyone.

## Fix
Two gates, because the release reaches the server by more than one road.

1. **`deploy.Validate`** (`server/deploy/validate.go`) refuses the push. The developer
   reads it in their terminal, the release is never activated, and the rejection lands
   in the deploy record like any other. This is where it should normally be caught.
2. **`Server.SwapRelease`** (`server/activate.go`) re-runs the check against the config
   that is about to serve — after carrying and validating, before anything is published
   — and refuses activation. The previous release keeps serving and the refusal is
   logged. This is the backstop for the roads that skip the gate: `--no-validate`, a
   `current` symlink moved by hand, a rollback to a release older than the gate.

Both gate on the repository existing, exactly as `initGit` does, and both take the site
root from the *running server's* or the *release's own location on disk*, never from the
file being checked.

The check itself moved to `config.CheckRepoOutsideServedRoots`
([`server/config/paths.go`](../../server/config/paths.go)) so all four callers share one
implementation. `basil check`'s `checkRepository` had a fourth, narrower copy that knew
nothing about `routes[].public_dir`, the uploads directory or `static[].file` — it could
report "not inside any served root" on a placement the server would refuse — and now
calls the same function.

Covered by `TestSwapReleaseRefusesReleaseThatServesTheRepository` and
`TestSwapReleaseAllowsStaticRootInsideTheRelease` (`server/activate_test.go`),
`TestValidateRejectsServedRootOverTheRepository` and
`TestValidateAcceptsStaticRootInsideTheRelease` (`server/deploy/validate_test.go`), and
`TestCheckRepoOutsideServedRoots` (`server/config/paths_test.go`, moved there with the
function).

## Not fixed here
The guard answers "would this release expose `site.git`?", not "should a release be able
to serve the site root at all?". A release pointing a static root at `<site root>` on a
site with no `site.git` still publishes `data/` and the databases under it. That is a
separate question about served-root containment in general — see backlog #156.
