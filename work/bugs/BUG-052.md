# BUG-052: `<p title={value}>` backslash-escapes quotes instead of HTML-escaping

## Summary

Interpolating a value into a tag attribute — `<p title={value}>` — escapes `"`
in the value as `\"` (backslash-quote). Backslash has no meaning in HTML
attribute syntax: a double-quoted attribute value ends at the next `"`,
whatever precedes it. So a value containing `"` closes the attribute early, and
anything after it is parsed as **new attributes** — including live event
handlers. This is an attribute-injection XSS wherever unescaped user input
(`@params`, form fields, query strings, a `string`/`text` DB field) reaches an
attribute value.

It also silently corrupts legitimate data: a `title` of `He said "hi"` renders
as `He said \"hi\"`, and the user sees the backslashes.

This is distinct from the raw-content-interpolation gap (`<p>userInput</p>`
inserts markup raw), which is documented and tracked by
[FEAT-151](../specs/FEAT-151.md). That gap is about `<`/`>` in tag *content*;
this bug is the *attribute* path doing escaping that looks protective but isn't,
and it bites even when the value contains no `<` or `>`.

## Reproduction

```parsley
let breakout = `x" onmouseover="alert(1)`
<p title={breakout}>"b"</p>
```

Rendered output:

```html
<p title="x\" onmouseover=\"alert(1)">b</p>
```

Chrome parses that as `title="x\"` **plus a live `onmouseover` event-handler
attribute** — verified in-browser: `p.hasAttribute('onmouseover')` is `true`.
No `<`/`>` involved, so content escaping (FEAT-151) would not catch it.

And the data-corruption case:

```parsley
<p title={`He said "hi"`}>"a"</p>
// renders: <p title="He said \"hi\"">a</p>   — backslashes visible to the user
```

## Cause

`evalTagProps` in `pkg/parsley/evaluator/eval_tags.go` (the `{expr}` attribute
branch, ~line 1345) writes the attribute value with a hand-rolled loop that
replaces `"` with `\"` and passes every other rune through unchanged. `\"` is
not an HTML entity; the browser sees a literal backslash followed by a
value-terminating quote. `&`, `<`, `>` in the value are also passed through raw.

The correct escaping already exists one file away: `escapeAttrValue` in
`pkg/parsley/evaluator/form_binding.go` maps `& < > "` to entities, which is
exactly right for a double-quoted attribute. The `@field` form path already
uses it; the general `{expr}` attribute path does not.

## Fix

Replace the backslash loop with `escapeAttrValue`. Scope, deliberately narrow:

- Only the `{expr}` attribute branch changes. Static attribute text and the
  single-quoted `'…@{}…'` raw-interpolation path are separate and untouched.
- Escaping `&` can double-encode a value that already contains an entity
  (`&amp;` → `&amp;amp;`). This is conventional (Rails, Jinja do the same) and
  is the safe direction; a test pins it as a decision rather than a surprise.

## Not in scope

- Content escaping / escape-by-default (the `Html` type) — [FEAT-151](../specs/FEAT-151.md).
- Context-aware escaping: a `javascript:` URL in `href={userInput}` is escaped
  as an attribute (quotes/entities) but survives as a working `javascript:` URL.
  Also FEAT-151's deferred territory. This fix closes the quote-breakout hole,
  not URL-context escaping.

## Verification

- Unit tests over `evalTagProps` output: quote-breakout payload, `&`/`<`/`>` in
  an attribute, the `He said "hi"` corruption case, double-encoding, and a
  null/false attribute still omitted.
- HTTP surface: a page that puts a hostile `@params` value into an attribute
  serves entity-escaped output; the browser parses no injected attribute.
