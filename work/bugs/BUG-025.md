# BUG-025: Logical AND (&&) operator does not short-circuit evaluation

## Summary

The `&&` (logical AND) operator in Parsley does not short-circuit: when the left-hand side is falsy, the right-hand side is still evaluated. This causes runtime type errors when the right-hand side depends on the left-hand side being truthy (a common guard pattern).

## Observed Behavior

```parsley
let x = null
if (x != null && x.length() > 0) "yes" else "no"
// Runtime error: Type mismatch: null > integer
```

Both sides of `&&` are evaluated even when `x != null` is false. `x.length()` is called on `null`, causing a type error.

The same issue applies to `||` (logical OR) — if the left side is truthy, the right side is still evaluated. However, `||` short-circuit failures are rarer in practice.

## Expected Behavior

```parsley
let x = null
if (x != null && x.length() > 0) "yes" else "no"
// Should return: "no"
```

When the left side of `&&` evaluates to falsy, the right side should NOT be evaluated. This is the standard short-circuit evaluation behavior found in virtually every programming language (JavaScript, Python, Go, Rust, C, Java, etc.).

## Reproduction Steps

1. Run: `pars -e 'let x = null; if (x != null && x.length() > 0) "yes" else "no"'`
2. Observe runtime error instead of "no"

## Workaround

Use nested `if` statements instead of `&&`:

```parsley
// Instead of: if (x != null && x.length() > 0) ...
if (x != null) {
    if (x.length() > 0) {
        "yes"
    } else {
        "no"
    }
} else {
    "no"
}
```

This workaround is verbose and un-idiomatic. It was used in the DataTable component (FEAT-144) for the footer null-check.

## Environment

- Parsley (all versions)

## Impact

- **Guard patterns fail**: The most common use of `&&` — null/type guards — causes runtime errors
- **Forces verbose workarounds**: Developers must use nested `if` instead of idiomatic `&&` guards
- **Surprising to all users**: Every mainstream language short-circuits logical operators
- **Affects component authors**: The DataTable component (FEAT-144) had to work around this with nested `if` checks in the footer section

## Investigation Notes

### Questions to Answer

Before fixing, determine whether non-short-circuit `&&` was an intentional design decision:

1. Check `work/specs/` and `work/design/` for any rationale about operator evaluation semantics
2. Check if any existing code relies on both sides of `&&` being evaluated (side effects)
3. Check `pkg/parsley/evaluator/` for the `&&` implementation — is it using `evalInfixExpression` which evaluates both sides before dispatching?

### Likely Root Cause

The `&&` operator is probably implemented as a standard infix expression where both operands are evaluated before the operator is applied. Short-circuit evaluation requires special handling — the operator must evaluate the left side first, check the result, and conditionally skip the right side.

### Affected Code

- `pkg/parsley/evaluator/` — wherever `&&` / `||` infix expressions are evaluated
