# BUG-029: String `[i]` / `[a:b]` count bytes, not characters

## Summary
Parsley's character-oriented string operations disagree on what a "character"
is. `.length()` and `for … in` iteration are **rune-based** (Unicode
codepoints), but `[i]` indexing and `[a:b]` slicing are **byte-based**. On any
string containing multi-byte UTF-8 characters, an index or slice can land in the
middle of a character and return an invalid partial byte.

This is the same byte-vs-rune class as [BUG-028] (raw-text scanning), but in the
evaluator's index/slice paths rather than the lexer.

## Reproduction
```parsley
"café".length()        // 4   — rune count
for (ch in "café") { ch }   // ["c", "a", "f", "é"]   — rune iteration

"café"[3]              // "Ã"    — expected "é"; returns byte 0xC3 (first byte of é)
"café"[-1]             // "©"    — expected "é"; returns byte 0xA9 (last byte of é)
"café"[0:4]            // "caf<invalid>"  — slices mid-character
"a中😀".length()        // 3
"a中😀"[1]              // partial byte of 中, not "中"
```
Pure-ASCII strings are unaffected (one byte == one character), so the bug only
bites on non-ASCII input.

## Expected
Indexing and slicing should be **rune-based**, consistent with `.length()` and
iteration:

- `"café"[3]` → `"é"`
- `"café"[-1]` → `"é"`
- `"café"[0:4]` → `"café"`

An index `i` is in range iff `0 <= i < .length()`; a slice `[a:b]` selects
characters `a` (inclusive) to `b` (exclusive) by character position.

## Suspected Location
`pkg/parsley/evaluator/eval_operators.go`:

- `evalStringIndexExpression` (~line 182) — uses `max := int64(len(stringObject.Value))`
  (byte length) and returns `string(stringObject.Value[idx])` (byte access).
- the string-slice path (~line 402) — clamps against byte `len(...)` and returns
  `stringObject.Value[startIdx:endIdx]` (byte slice).

Both should convert to `[]rune` first (as `.length()` at
`methods_string.go:293` and the `for … in` loop at
`eval_control_flow.go:61` already do), index/slice the rune slice, then
`string(...)` the result. Note `max` must become the **rune** count so
out-of-range detection lines up with `.length()`.

## Impact / Risk
- Correctness: silently produces invalid UTF-8 (`�`) for non-ASCII text.
- Consistency: `s[i]` and `s.length()` use different units, so
  `s[s.length() - 1]` is not "the last character" for non-ASCII strings.
- Behaviour change: switching to runes changes results for any code currently
  relying on byte indices (likely rare, but worth a note in the changelog).
  Out-of-range errors (`INDEX-0001`) and optional access (`[?n]`) semantics
  should be preserved.

## Docs
The current (byte) behaviour is documented as a ⚠️ caveat in
`docs/parsley/manual/builtins/strings.md` ("Text & Unicode" and "Indexing &
Slicing" sections) and cross-referenced from
`docs/parsley/manual/fundamentals/control-flow.md`. When this is fixed, those
caveats should be removed and the examples updated to the rune-based results.

## Found
Auditing the manual's string documentation — the Control Flow page described
`for … in` as iterating "individual characters" without defining the unit;
verifying against the evaluator surfaced the index/iterate split.

## Resolution
Fixed in `pkg/parsley/evaluator/eval_operators.go`. Both string paths now
convert to `[]rune` before indexing/slicing:

- `evalStringIndexExpression` — `max` is the rune count and the result is
  `string(runes[idx])`, so negative indices, `INDEX-0001` out-of-range
  detection, and optional `[?n]` access all line up with `.length()`.
- `evalStringSliceExpression` — clamps and slices against rune positions and
  returns `string(runes[startIdx:endIdx])`, so a boundary never lands inside a
  multi-byte character. `INDEX-0001` (negative), `INDEX-0003` (start > end),
  and beyond-length clamping are preserved, now measured in runes.

Verified against the reproduction with `pars -e`:

- `"café"[3]` → `"é"`, `"café"[-1]` → `"é"`, `"café"[0:4]` → `"café"`
- `"a中😀"[1]` → `"中"`
- `"café"[4]` → `INDEX-0001` (rune length 4), `"café"[?9]` → `null`

Added `TestEvalStringIndexExpressions` and `TestEvalStringSliceExpressions`
covering ASCII, multi-byte, negative, out-of-range, optional, and clamping
cases (`pkg/parsley/evaluator/evaluator_test.go`). Docs updated
(`docs/parsley/manual/builtins/strings.md` now states indexing/slicing is
character-based with a multi-byte example) and a CHANGELOG entry added under
`[Unreleased]` noting the behaviour change for byte-index-reliant code.

This is the evaluator-side counterpart to [BUG-028] (the lexer's raw-text
byte-vs-rune bug).
