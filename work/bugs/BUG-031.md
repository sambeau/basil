# BUG-031: `[` at line start continues the previous expression as indexing

## Summary
When a statement ends and the next line begins with `[`, the parser treats the
bracket as an **index operation on the previous expression** rather than the
start of a new array-literal statement. A newline does not terminate the
expression, so:

- a multi-element array literal fails to parse (`expected ']', got ','`), and
- a **single-element** "array literal" parses silently as indexing, evaluating
  to the wrong value (or a runtime index error) with no hint that the program
  was misread.

## Reproduction
```parsley
let a = 1
[1, 2]
// Parser error: line 2, column 3
//   expected ']', got ','
```

Silent misparse (no error, wrong semantics):

```parsley
let xs = [10, 20, 30]
[0]
// parses as `let xs = ([10, 20, 30][0])` → xs is 10, and the program
// has no second statement — the "array literal" vanished
```

Also bites after expression statements:

```parsley
"some output"
[1, 2, 3]      // parser error: tries to index the string with `1, 2, 3`
```

## Expected
Either of these, decided deliberately:

1. **Newline-sensitive postfix**: an index/slice bracket must start on the
   same line as the expression it indexes (the approach JS-style ASI and Swift
   take). `[` at the start of a new statement line always begins an array
   literal.
2. At minimum, keep current parsing but this seems hard to justify — there is
   no way to write a top-level array literal after another statement without
   this trap.

Option 1 matches how the language already treats other statement boundaries
(no semicolons required between statements on separate lines).

## Suspected Location
`pkg/parsley/parser/parser.go` — the Pratt-parser loop that consumes postfix
operators (`parseIndexExpression` / `LBRACKET` as an infix/postfix token)
doesn't consider line breaks when deciding whether `[` continues the current
expression. The lexer records token line numbers, so the parser can compare
the `[` token's line against the end of the left expression.

## Impact / Risk
- Multi-element case is an immediate, confusing parse error far from the real
  cause (the error points at the comma, not at the statement boundary).
- Single-element case silently changes program meaning — worst kind of parse
  ambiguity.
- Workarounds exist (assign the array to a variable, or put the literal first)
  but nothing in the error message suggests them.
- Fix is a behaviour change: any existing code deliberately splitting
  `expr` / newline / `[index]` across lines would need the bracket moved back
  onto the expression's line. Likely rare; needs a CHANGELOG note.

## Found
While verifying the BUG-029 follow-up (Unicode audit) through the `pars` CLI:
a verification script ending in `[bv, gv]` on its own line failed with
`expected ']', got ','` because the array literal was parsed as an index into
the previous `let` statement's value.
