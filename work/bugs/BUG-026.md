# BUG-026: EXIF orientation dimension mismatch between imageInfo() and image transforms

## Summary
`imageInfo()` reports raw file dimensions (pre-EXIF rotation) while `image()` and `imageSrcset()` transforms operate on post-EXIF-rotation dimensions, causing incorrect metadata, aspect ratio calculations, and upscale clamping for rotated JPEGs.

## Observed Behavior
For a portrait-oriented JPEG with EXIF orientation tag (e.g., a 4000×3000 photo taken in portrait mode, stored as 3000×4000 with orientation=6):

1. `imageInfo(@./photo.jpg)` returns `{width: 3000, height: 4000}` (raw file dimensions, pre-rotation)
2. `image(@./photo.jpg, {width: 800})` produces an 800×600 image (post-rotation landscape dimensions applied correctly by `imaging.AutoOrientation`)
3. `imageSrcset()` uses the `imageInfo()` dimensions for aspect ratio and upscale clamping, so:
   - Aspect ratio calculation uses wrong width/height ratio (portrait instead of landscape)
   - Upscale clamping uses `srcWidth=3000` instead of the effective post-rotation `srcWidth=4000`
   - The returned `height` in the srcset dict is computed incorrectly

## Expected Behavior
`imageInfo()` should return dimensions consistent with what the transform pipeline actually operates on. For JPEGs with EXIF rotation (orientations 5–8 which swap width/height), the reported dimensions should reflect the post-rotation image — i.e., what the user actually sees.

## Reproduction Steps
1. Take or obtain a JPEG photo with EXIF orientation tag that swaps width/height (orientation values 5, 6, 7, or 8 — common on phone photos taken in portrait mode)
2. Call `imageInfo(@./photo.jpg)` — observe width and height are the raw (pre-rotation) dimensions
3. Call `image(@./photo.jpg, {width: 400})` and inspect the output — observe the actual output has post-rotation dimensions
4. Call `imageSrcset(@./photo.jpg, {width: 400}, [200, 400, 800])` — observe the `height` value in the returned dict does not match the actual aspect ratio of the generated variants

## Environment
- Affects all platforms
- All Go/Basil versions with FEAT-148 image builtins

## Investigation Notes

### Root Cause
The inconsistency is in the metadata path vs the transform path:

- **Metadata path** (`GetImageInfo` → `image.DecodeConfig`): Reads raw file dimensions from the image header. `image.DecodeConfig` does not interpret EXIF metadata, so it returns the stored pixel dimensions before any rotation is applied.

- **Transform path** (`Load` → `imaging.Open` with `AutoOrientation(true)`): Reads EXIF orientation tag and applies the rotation/flip, which may swap width and height (for orientations 5–8). The transformed image has correct visual dimensions.

This means `Info()` and `Transform()` in the registry disagree on the dimensions of the same source image when it has a non-trivial EXIF orientation.

### Affected Code
- `server/images/transform.go:GetImageInfo()` — uses `image.DecodeConfig` which returns raw (pre-EXIF) dimensions
- `server/images/transform.go:GetInfo()` — calls `GetImageInfo`, propagates incorrect dimensions
- `server/images/registry.go:Info()` — caches and returns the incorrect dimensions
- `pkg/parsley/evaluator/image.go:evalImageSrcset()` — uses `Info()` for `srcWidth`/`srcHeight` to compute aspect ratio and clamp widths

### Affected Builtins
- `imageInfo()` — returns wrong width/height for rotated JPEGs
- `imageSrcset()` — computes wrong aspect ratio and clamping from `imageInfo()` data
- `image()` — not directly affected (transforms are correct), but users who combine `imageInfo()` with `image()` will see inconsistent data

### Impact
- **Severity**: Medium — only affects JPEGs with EXIF rotation tags (orientations 5–8). Landscape photos, PNGs, GIFs, and WebP are unaffected. However, phone-taken portrait photos are extremely common and this is the primary scenario where users would notice wrong dimensions.
- **Functional impact of `imageSrcset()`**: The `height` value in the returned dict will be wrong, and width clamping may allow requesting widths larger than the effective source (since the raw dimension may be larger than the rotated dimension on one axis).

### Possible Fix Approaches

**Option A: EXIF-aware `GetImageInfo`**
Read the EXIF orientation tag alongside `image.DecodeConfig` and swap width/height when orientation is 5–8. This avoids fully decoding the image. Requires reading the EXIF data (e.g., via `github.com/rwcarlsen/goexif/exif` or manual EXIF parsing of just the orientation tag).

**Option B: Use `imaging.Open` in `GetInfo`**
Fully decode the image with auto-orientation to get correct dimensions. This is correct but slower — defeats the purpose of the efficient `DecodeConfig` path. Could be mitigated by the `sync.Map` info cache (only pays the cost once per source+modtime).

**Option C: Hybrid — `DecodeConfig` + EXIF orientation check for JPEGs only**
Use `DecodeConfig` for dimensions, but for JPEG files also read the EXIF orientation tag and swap width/height if needed. Other formats don't have EXIF orientation, so no change needed for PNG/GIF/WebP.

Option C is likely the best balance of correctness and performance.

## Resolution

### Fix Description
Implemented Option C: added a `readJPEGOrientation()` function in `server/images/transform.go` that reads the EXIF orientation tag directly from JPEG files by parsing the APP1/EXIF segment (SOI → APP1 marker → EXIF header → TIFF byte order → IFD entries → orientation tag 0x0112). This is the same approach used internally by `disintegration/imaging` but reimplemented since their function is unexported.

`GetImageInfo()` now calls `readJPEGOrientation()` for JPEG files and swaps width/height when the orientation is 5–8 (transpose, rotate 270, transverse, rotate 90). Non-JPEG formats and JPEGs without EXIF data are unaffected.

This ensures `imageInfo()`, `imageSrcset()` aspect ratio calculations, and upscale clamping all use post-orientation dimensions consistent with what `image()` transforms produce.

No new dependencies were added — the EXIF parsing uses only `encoding/binary` and `io` from the standard library.

### Test Coverage
Added to `server/images/transform_test.go`:
- `createTestJPEGWithOrientation()` — helper that creates a JPEG with a synthetic EXIF APP1 segment containing a specified orientation tag
- `TestReadJPEGOrientation` — verifies all 8 orientation values are correctly read
- `TestReadJPEGOrientation_NoEXIF` — verifies plain JPEG without EXIF returns 0
- `TestReadJPEGOrientation_PNG` — verifies non-JPEG files return 0
- `TestGetImageInfo_EXIFOrientationSwapsDimensions` — table-driven test covering orientations 1, 3, 5, 6, 7, 8 with expected dimension swap behavior
- `TestGetInfo_EXIFOrientationAffectsOrientationField` — verifies the `orientation` field ("portrait"/"landscape"/"square") reflects post-rotation dimensions
- `TestGetImageInfo_NoEXIF_DimensionsUnchanged` — regression: plain JPEG dimensions unchanged
- `TestGetImageInfo_PNG_DimensionsUnchanged` — regression: PNG dimensions unchanged
