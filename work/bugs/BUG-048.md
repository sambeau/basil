# BUG-048: dev mode was never not caching, it was only being told

## Summary
A stray `a` was removed from `components/shows/shows.pars` and `basil --dev`
went on serving the error it caused:

```
… /components/shows/shows.pars: line 8, column 64: Identifier not found: `a`
2026-08-27T09:53:05+01:00 GET / 500 5.991167ms
```

The file on disk was correct. The module cache was not, and nothing was going
to correct it.

This is the third bug of the same shape — BUG-043 was the second — so the
report is less about the stale module than about why they keep arriving.

## Cause
Basil keeps four caches. Three of them ask whether caching is on:

| cache | dev-aware | where |
|---|---|---|
| `responseCache` | yes | `cacheDisabled: devMode && !cacheEnabled` |
| `fragmentCache` | yes | `if c.devMode \|\| c.disabled` |
| `scriptCache` (page ASTs) | yes | `if c.devMode { return c.parseScript(path) }` |
| **`moduleCache`** (every `import`) | **no** | — |

`moduleCache` is a process-global in `pkg/parsley/evaluator` with no server
wiring at all. It cached unconditionally and left dev-mode freshness entirely
to the file watcher calling `InvalidateModule`. So the property was never "dev
mode does not cache". It was **"dev mode caches, and hopes an fs event
arrives"** — and a page is mostly components, so almost all the code you edit
in a day goes through the one cache that was working that way.

The irony is that the field for this already existed, and its comment said what
it was for:

```go
DevMode bool // Whether dev mode is enabled (affects caching)
```

`importModule` never read it. It was also not copied into `moduleEnv`
alongside `Security`, `DevLog`, `BasilCtx` and the rest, so it did not reach a
module's own imports either.

### Three ways the watcher misses
Each is enough on its own to serve stale code until restart.

**A directory created after startup is never watched.** `watchDirRecursive`
runs once in `Start`, and fsnotify watches a directory, not its future
children. Reproduced at the HTTP surface — component edited, no `[WATCH]` line
logged, page frozen:

```
disk:   SLOW-THREE
served: SLOW-ONE
```

Writing a component and then editing it is the ordinary way a component comes
into existence, so this is not an edge case; it is the first hour of any new
component's life.

**The debounce discarded events instead of coalescing them.** The window was
global rather than per-file and hit `continue`, so a Save All across two files
dropped the second file's change outright — no reload, no invalidation, and
nothing left to notice it later.

**The cache write races the invalidation.** `importModule` reads the file,
evaluates it, then stores the result. A request that started before an edit
finishes after it and re-inserts the pre-edit module into a cache the watcher
has already cleared. Stale, with nothing left to invalidate it.

They share a root: correctness depended on an event, so every gap in event
delivery was a correctness gap. BUG-043 patched one gap. This is the pattern
underneath it.

## Fix
The first attempt was to stop caching modules in dev altogether. That works and
is wrong: the point was never to avoid caching, it was to notice changes. It
cost 2.9x on a component-heavy page, for a page where nothing had changed.

**A cached module now records what it was built from and checks it.** Each
entry carries the modification time and size of every file it came from, and in
dev mode is served only if they all still agree. The watcher stops being
load-bearing for correctness and goes back to what it is for — reloading the
browser.

**The stamps cover the transitive closure, not the file.** `environmentToDict`
returns `&Dictionary{Pairs: pairs, Env: env}`, so a cached module carries its
own environment with its nested imports already resolved inside it. An entry
stamped only against its own path would serve a component built against last
week's copy of a helper it imports — silently, and worst for the helper shared
most widely. `TestModuleCache_RereadsOnTransitiveChange` is that case, and it
fails if `store` is reduced to stamping one file.

**The stamp is taken before the file is read, never after.** That is what makes
the third failure above impossible rather than merely unlikely: a request that
began before an edit and finished after it stores an entry describing the
pre-edit file, so the entry fails its own next validation.

**Revalidation is the default; trusting the cache is the opt-out.**
`Environment.TrustModuleCache` is set only where the sources cannot change
under the running evaluation - a production release, or `dev.cache` - and the
server is the only thing that sets it. Everything else, the `pars` CLI and the
REPL included, revalidates without having to know the field exists.

The polarity is the point. Getting this wrong by omission now costs a stat per
import; getting it wrong the other way round is this bug, and it took three of
them to notice. `TestModuleCache_DefaultEnvironmentRevalidates` pins it.
`Environment.TrustModuleCache` propagates into module environments so nested
imports obey it too.

`Environment.DevMode` is renamed `NoCache` and now means only what it says —
do not serve `<basil.cache.Cache>` fragments from cache, a fragment having
nothing to check itself against. A field called `DevMode` that two caches were
supposed to consult, and only one did, is how this drifted; the two caches now
have separate fields because they genuinely answer differently.

`ClearModuleCache` and `InvalidateModule` are kept but are no longer required
for correctness — the former for release activation, where cached modules may
hold the outgoing release's database connections, the latter as a cheap
belt-and-braces that does not depend on file stamps at all.

The watcher is fixed too, since live reload still depends on it: new
directories are watched as they appear, and the debounce is keyed per file so
one save cannot swallow another's.

## Cost
A page importing 20 components that share a helper, per request:

| | ns/op | allocs/op |
|---|---|---|
| dev, not caching | 2,820,000 | 21,022 |
| dev, stamped | 959,000 | 7,096 |
| production | 855,000 | 6,600 |

Stamped dev is within 12% of production, and most of that gap is the page AST
re-parse `scriptCache` already did in dev rather than the stats — 21 files is
about 2%.

## Verification
- The reproduction above, on the fixed binary: component edited in a directory
  created after startup, picked up on the very next request, no watcher event
  involved.
- `TestModuleCacheDevModeSeesEdits` — fails on the old code
  (`expected version 2, got 1`), passes on the new. No watcher runs in it, and
  the file it edits is two imports down from the handler with the component
  between them untouched.
- `TestModuleCacheProductionCaches` and `TestModuleCacheDevCacheOptsBackIn` —
  the other half of the spec, and they pass both before and after by design: a
  fix that made dev fresh by making everything uncached would pass the first
  test and fail these.
- `TestModuleCache_ServesUnchangedModuleFromCache` — that dev mode still caches
  cannot be seen from the request surface, since a correct answer looks the
  same either way. The evaluator-level tests compare the returned `*Dictionary`
  by identity, which distinguishes a reused entry from a re-evaluated one.
- `TestModuleCache_RereadsOnTransitiveChange` and
  `TestModuleCache_StaleWriteLosesToItsOwnStamp` — the closure and the
  stamp-before-read, each verified to fail when its mechanism is removed.
- `TestModuleCache_DefaultEnvironmentRevalidates` — the polarity of
  `TrustModuleCache`. Nothing outside the server sets the field, so this test
  is what keeps the CLI, the REPL and any embedder right.
- The REPL driven through an edit mid-session, against binaries built either
  way round: stale before, current after.
- `TestWatcher_WatchesDirectoriesCreatedAfterStart` and
  `TestWatcher_DebounceIsPerFile` — both fail on the old watcher.
- `go build ./...`, `go vet ./...`, `go test ./...`, and the watcher tests
  under `-race`.

## Notes
The residual gap in stamping is a write landing within the filesystem's mtime
resolution of the previous one, at an unchanged size. On APFS and ext4 that
resolution is a nanosecond. `InvalidateModule` is retained partly against a
filesystem where it is not.

The REPL and the `pars` CLI revalidate, as development tools should. In a REPL
session, importing a file, editing it and importing it again used to return the
first copy:

```
VERSION-ONE
VERSION-ONE     before
VERSION-TWO     after
```

Neither sets anything to get this; they get it by being ordinary callers of
`NewEnvironment`.

**The truncated log line in the report is not a defect.** The full line is
`script error in <page>: in <component>: line N, column N: …` with two absolute
paths, and the terminal cut it. Worth noting anyway: the error *page* shows
paths relative to `ReleaseDir` and the log does not, so the log line is far
longer than it needs to be. Left alone here.

The suspicion that this was a recent regression did not hold up. `git log -S`
found `9bbdb24` removing per-request `ClearModuleCache()` from `api.go`, which
looks like the culprit and is not — page handlers never cleared it, so pages
have depended on the watcher the whole time. What changed is not the caching
but the exposure: more components, in more subdirectories, created while the
server is up.
