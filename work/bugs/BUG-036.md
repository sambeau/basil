# BUG-036: a recursive delete could carry off a path the write deny list protected

## Summary
The Parsley evaluator's write-sandbox deny list (`SecurityPolicy.RestrictWrite`, checked
in `checkPathAccess` at `pkg/parsley/evaluator/eval_helpers.go` via `isPathRestricted`)
only ever asked the **forward** question: *is the operated-on path itself inside a denied
entry?* It never asked the inverse: *does the operated-on directory contain a denied
entry?*

That is enough for a normal write, which names its exact victim. It is **not** enough for
a recursive directory removal (`os.RemoveAll`), which names an *ancestor* and takes every
descendant with it. The denied entry is then a descendant the forward check never sees, so
a recursive delete of a parent of a denied file passed the check and `os.RemoveAll` took
the denied file with it.

FEAT-156 added `RestrictWrite` entries for the deploy record and the auth database
(`server/deploy/engine.go`, `sandboxDeniedWrites`) to stop a push-triggered `deploy.pars`
hook from touching them. But the hook's `AllowWrite` is the whole `DataDir`, and both
databases live inside it, so:

```parsley
dir(path("../../data")).rmdir({recursive: true})
```

in a pushed release's `deploy.pars` (or a recursive delete of any ancestor) still destroyed
the deploy record and the auth database — the exact files the deny list was added to
protect.

## Reproduction
`TestDeleteTreeInverseContainment` (`pkg/parsley/evaluator/file_path_security_test.go`) is
the unit written down: the same parent directory checked as `"write"` passes (the forward
check misses the descendant) while checked as `"delete-tree"` it is refused.
`TestDeployHookPushSandboxRefusesRecursiveDeleteOfDataDir`
(`server/deploy/engine_test.go`) is the bug end to end: a sandboxed hook recursively
deleting the data dir is refused, the deploy still completes (hook failure is recorded, not
fatal), and the auth database survives with its contents intact.

## Fix
Recursive removal is now a **distinct sandbox operation**, `"delete-tree"`, stated once in
`checkPathAccess` (`pkg/parsley/evaluator/eval_helpers.go`). It runs the normal write
restriction check *and* additionally refuses when any `RestrictWrite` entry **equals or
sits beneath** the target — `entry == absPath || strings.HasPrefix(entry, absPath + sep)`,
after resolving each denied entry through `EvalSymlinks` exactly as `isPathRestricted`
does. The inverse test lives in a new helper, `restrictedEntryUnder`, next to
`isPathRestricted`.

The recursive delete call site (`rmdirFromDict`, `pkg/parsley/evaluator/methods_file_http.go`)
selects `"delete-tree"` when `recursive: true` and keeps `"write"` for the non-recursive
`os.Remove`. The other non-recursive site (`evalFileRemove`,
`pkg/parsley/evaluator/eval_file_io.go`) is unchanged and keeps `"write"`.

Nothing else changes: no other operation's semantics, no change to what populates
`RestrictWrite`, and no widening of any sandbox. This fix is what makes FEAT-156's
guarantee — the deploy record and auth database "cannot [be] touch[ed]" by a push hook —
hold against the deletion vector as well as the write vector.

Covered by `TestDeleteTreeInverseContainment`, `TestDeleteTreeViaRmdirMethod` and
`TestDeleteTreeSymlinkedTarget`
(`pkg/parsley/evaluator/file_path_security_test.go`), and
`TestDeployHookPushSandboxRefusesRecursiveDeleteOfDataDir`
(`server/deploy/engine_test.go`).

## Not fixed here
- **Rename.** A hook that could rename an ancestor directory would move a denied file out
  of the deny list's reach just as effectively as deleting it. Parsley has no rename/move
  method exercised by this path today, but `checkPathAccess` has no `"rename"` operation
  and would not apply the inverse check if one were added — the same class of hole.
- **Hardlink.** If a hook could hardlink a denied file to a fresh name inside its writable
  area, the deny list (which matches by path) would not cover the new name. No hardlink
  builtin is wired through the sandbox today; noted for whoever adds one.
- **TOCTOU.** The check and the `os.RemoveAll` are separate steps against a path string; a
  concurrent symlink swap of an intermediate component between check and removal is a
  classic time-of-check/time-of-use gap. Not exploitable from a single-threaded hook run
  in the current deploy path, but the check is path-based, not fd-based.
- **A denied entry that does not exist yet.** `restrictedEntryUnder` (like
  `isPathRestricted`) keeps the raw path when `EvalSymlinks` fails, which it does for a
  path that does not exist. Prefix comparison still holds when the target directory *does*
  resolve, but if the two sides resolve in different namespaces (e.g. macOS `/var` vs
  `/private/var`) because only one exists, containment could be missed. In the deploy path
  the data dir exists at deploy time, so both sides resolve consistently; a deny entry
  named before its parent exists is the fragile case.
