# BUG-033: `git push` to a Basil server is rejected out of the box

## Summary
The workflow documented in [`docs/guide/git.md`](../../docs/guide/git.md) — clone the
site, edit, `git push`, site reloads — does not work on a fresh install. Two separate
gaps, both in the same area:

1. **Basil never creates the repository.** `basil --init` writes a `.gitignore` but
   never runs `git init`, and the server never initialises one either. A newly created
   project has no repository for `/.git/` to serve.
2. **Basil never configures receive behaviour.** The served repository *is* the live
   site directory — a non-bare repo with a checked-out working tree. Git refuses by
   default to accept a push into the branch that is checked out, and nothing in Basil
   sets `receive.denyCurrentBranch`.

So even an operator who works out gap 1 for themselves hits gap 2 on their first push.

FEAT-035 is marked `implemented` and the guide describes the feature as working, so this
is a documentation/behaviour mismatch as much as a code defect.

## Reproduction

```bash
basil --init mysite          # no repository is created
cd mysite
git init -b main . && git add -A
git -c user.email=a@b -c user.name=a commit -m init
# ... enable git in basil.yaml, start the server, clone from it, edit, then:
git push
```

Verified locally against a plain non-bare repo (the same shape `server/git.go` serves):

```
remote: error: refusing to update checked out branch: refs/heads/main
remote: error: By default, updating the current branch in a non-bare repository
remote: is denied, because it will make the index and work tree inconsistent
remote: with what you pushed, and will require 'git reset --hard' to match
remote: the work tree to HEAD.
 ! [remote rejected] main -> main (branch is currently checked out)
error: failed to push some refs to '.../site'
```

### The second failure mode

Setting `receive.denyCurrentBranch=updateInstead` fixes the first push, but git then
refuses any push while the live working tree has **uncommitted changes to tracked
files**. Also verified locally:

```
 ! [remote rejected] main -> main (Working directory has unstaged changes)
error: failed to push some refs to '.../site'
```

A long-running site drifts into that state as soon as anything writes inside a tracked
path, and the operator gets a rejected deploy with no obvious cause. Note this is about
*tracked* files — untracked and ignored files (`db/`, `logs/`, `certs/`) do not trigger
it.

## Cause

`server/server.go:576` points the handler at the project directory:

```go
siteDir := s.config.BaseDir
gitHandler, err := NewGitHandler(siteDir, s.authDB, s.config, onPush, ...)
```

`NewGitHandler` (`server/git.go:30`) passes that straight to `githttp.New(siteDir)`, and
`go-git-http` shells out to the real `git` binary with `cmd.Dir` set to it. So Basil
inherits stock `git receive-pack` behaviour for a non-bare repository, which is to
refuse. Nothing anywhere in the tree mentions `denyCurrentBranch`, `updateInstead`, or
`push-to-checkout`, and `cmd/basil/init.go` only writes `.gitignore`.

Related: `docs/guide/git.md` states that "the `go-git-http` handler writes files to the
site directory". It does not — it runs `git receive-pack`, which updates refs. The
working tree is only touched if receive behaviour has been configured to do it. The
`onPush` callback (`server/server.go:579`) clears three caches and assumes the files are
already there.

## Expected behaviour
`git clone`, edit, `git push` works on a fresh install with no undocumented manual
setup, and a push does not start failing because the live tree has drifted.

## Suggested fix

Short term, keeping the current single-directory layout:

- `basil --init` initialises a git repository alongside the `.gitignore` it already
  writes.
- When `git.enabled` is true, Basil ensures the repository exists and sets
  `receive.denyCurrentBranch=updateInstead` (or installs a `push-to-checkout` hook,
  which also lets us decide what to do about a drifted tree rather than just refusing).
- Fix the "writes files to the site directory" paragraph in `docs/guide/git.md` and
  document the drifted-tree failure.

Longer term this whole class of problem disappears under
[`DESIGN-git-deploy-topology.md`](../design/DESIGN-git-deploy-topology.md), which
separates the pushed-to repository from the live working tree so pushes never contend
with a checked-out branch at all. **The short-term fix above is still worth doing** — it
is small, it makes a shipped feature work as documented, and it does not conflict with
that design.

## Scope decision (2026-08-24)

The structural fix belongs to **FEAT-154**, which replaces the served repository with a
bare one — pushes then never contend with a checked-out branch, and this class of problem
disappears. Doing the full short-term fix as well would mean writing code we delete a
few weeks later: `basil --init` would create a non-bare repository that FEAT-152 then
re-creates as a bare one, and the `receive.denyCurrentBranch` configuration becomes
meaningless.

`git.enabled` defaults to `false` (`config.go:345`), so nobody reaches this without
deliberately turning the feature on.

**This bug is therefore scoped to the parts that are not throwaway:**

1. **Documentation.** `docs/guide/git.md` currently describes a workflow that does not
   work and states that the handler "writes files to the site directory", which it does
   not. Correct it, document the manual `receive.denyCurrentBranch=updateInstead` step
   required to use the feature today, and note the drifted-tree failure mode.
2. **`.gitignore`.** Add `cache/` to the template in `cmd/basil/init.go` — the default
   image cache directory sits in a tracked path today.
3. **Optionally, a fail-fast check.** When `git.enabled` is true, verify at startup that
   the directory is a repository with workable receive settings, and log a clear error if
   not, rather than letting the operator meet a cryptic Git rejection. ~10 lines.

Everything else — creating the repository, configuring receive behaviour — is delivered
by FEAT-152 and FEAT-154 and is tracked there. This bug closes when FEAT-154 lands and its
regression test passes.

## Resolution status (2026-08-24)

**The scoped part of this bug is done** and merged to `main` as
`a2487ab` — *"docs(git): correct the Git deploy guide; gitignore cache/ (BUG-033, phase 0)"*.

Delivered against the Scope decision above:

1. **Documentation — done.** `docs/guide/git.md` no longer claims the handler "writes
   files to the site directory"; it describes what `git receive-pack` actually does,
   documents the manual `git init` and
   `git config receive.denyCurrentBranch updateInstead` needed to use the feature today,
   and covers the `Working directory has unstaged changes` drifted-tree failure and how
   to clear it. The guide's user and API-key commands were corrected to the ones the CLI
   actually implements, and the example YAML now includes the `auth.enabled: true` that
   `git.require_auth: true` requires.
2. **`.gitignore` — done.** `cache/` is now in the template written by `basil --init`
   (`cmd/basil/init.go`), covered by `cmd/basil/init_test.go`.
3. **Fail-fast startup check — not done.** This was listed as optional. No startup
   validation of the repository or its receive settings was added.

**The structural fix remains open and is owned by FEAT-154** (PLAN-132 phase 3), which
replaces the served repository with a bare one so a push never contends with a
checked-out branch. No repository-creation or receive-configuration code was added here
deliberately: it would be code FEAT-152/FEAT-154 delete, and `receive.denyCurrentBranch`
becomes meaningless once the repo is bare. `git.enabled` still defaults to `false`, so
nobody reaches this by accident.

**This bug closes when FEAT-154 lands with its regression test.** It stays open until then.

## Notes
- The `.gitignore` shipped by `basil --init` covers `logs/`, `db/`, `*.db` and `certs/`
  but not `cache/`, which is the default image cache directory
  (`config.go:350`, `./cache/images`). A transformed-image cache inside a tracked path
  is exactly the kind of drift that triggers the second failure mode. Worth adding while
  fixing this.
