# BUG-032: User-defined functions never check arity

## Summary
Calling a user-defined (`fn`) function with the wrong number of arguments is
never reported:

- **Too many** — the extra arguments are silently discarded.
- **Too few** — the unbound parameters are simply absent from the function's
  environment. The first *use* of one fails with `Identifier not found`, which
  points at the parameter inside the body rather than at the call site, and
  can even suggest another parameter name as a typo fix.

Built-in functions and methods enforce arity strictly (`ARITY-0001`,
`ARITY-0004`, `ARITY-0006`, …), so the language is inconsistent with itself.
The behaviour is documented in
[`functions.md`](../../docs/parsley/manual/fundamentals/functions.md) ("Extra
arguments are silently ignored … User-defined functions do not [enforce arity]")
but it was never a recorded decision — see *Cause* below.

## Reproduction
```parsley
let add = fn(a, b) { a + b }
add(1, 2, 3, 4)                 // 3 — the 3 and 4 vanish with no error

let one = fn(a) { a }
one()
// Runtime error: line 2, column 19
//   Identifier not found: `a`        ← points inside the body, not at one()
//     let one = fn(a) { a }; one()
//                       ^
```

A mistyped call with a parameter name nearby is actively misleading:

```parsley
let greet = fn(name, greeting) { greeting + ", " + name }
greet("Sam")
// Identifier not found: `greeting`
// hint: Did you mean `name`?       ← wrong diagnosis; the call is short an argument
```

## Cause
There is no code to check it. `extendFunctionEnv` in
[`eval_expressions.go`](../../pkg/parsley/evaluator/eval_expressions.go) binds
parameters positionally and stops at whichever of `fn.Params` / `args` runs out
first:

```go
for paramIdx, param := range fn.Params {
    if paramIdx >= len(args) {
        break            // too few: remaining params left unbound
    }
    ...                  // too many: trailing args never looked at
}
```

No design doc, spec, or decision record in `work/` discusses user-function
arity; the only "arity" references are to builtin/method arity checks
(FEAT-110, FEAT-054). The manual sentence was added with the fundamentals
section (commit `6f968eb`) and documents what the code happened to do.

### Why it has been harmless so far
Several internal call sites pass a *fixed* number of arguments to a user
callback regardless of how many parameters it declares, and rely on the extras
being dropped:

| Site | Passes | Declared by user |
|---|---|---|
| Tag/component dispatch ([`eval_tags.go`](../../pkg/parsley/evaluator/eval_tags.go) ×3) | 1 (props dict) | often `fn()` for prop-less components — `<C/>` works today |
| `.reduce` ([`methods_array.go`](../../pkg/parsley/evaluator/methods_array.go)) | 2 (`acc, elem`) | could be `fn(acc)` |
| Table `.where`/`.select`/`.map`/… ([`stdlib_table.go`](../../pkg/parsley/evaluator/stdlib_table.go)) | 1 | 1 |
| Array `.map`/`.filter`/`.find` ([`methods.go`](../../pkg/parsley/evaluator/methods.go)) | 1 | 1 |
| `.replace` with a function ([`methods.go:205`](../../pkg/parsley/evaluator/methods.go)) | 1 + groups only if `len(fn.Params) > 1` | adapts |
| `for (x in …) fn` / dict iteration ([`eval_control_flow.go`](../../pkg/parsley/evaluator/eval_control_flow.go)) | 1 or 2, chosen from `fn.ParamCount()` | adapts, errors on anything else (`LOOP-0004/0006`) |

So the codebase already has two styles: *adapt to the callee's arity* (for-loops,
`.replace`) and *pass a fixed count and hope* (tags, `.reduce`). The former is
the one to standardise on.

## How other scripting languages behave
| Language | Too many | Too few |
|---|---|---|
| JavaScript | ignored (`arguments`/rest collects them) | params are `undefined` |
| Lua | ignored | params are `nil` |
| PHP (user fns) | ignored | `ArgumentCountError` (7.1+) |
| Python | `TypeError` | `TypeError` |
| Ruby | `ArgumentError` | `ArgumentError` |
| Elixir / Erlang | arity is part of the function's identity — no match | no match |
| Go, Swift, Rust | compile error | compile error |

Parsley currently sits with JavaScript/Lua on "too many" but is *worse* than
either on "too few": JS and Lua bind the missing parameters to a value, so the
error (if any) is a clear `undefined`/`nil`; Parsley leaves the name unbound
and reports it as an unknown identifier. And unlike JS/Lua, Parsley has no
`arguments`/varargs for named functions, so dropping extras buys nothing.

Parsley already behaves like the strict camp for builtins, methods, and loop
callbacks. Extending that to `fn` is the consistent choice; the lenient
behaviour is an accident, not a feature.

## Expected
Calling a user-defined function with the wrong number of arguments should be
an `ARITY` error at the call site, the same class builtins raise:

```
Runtime error: line 2, column 1
  add expects 2 arguments, got 4
    add(1, 2, 3, 4)
    ^
```

Proposed rules:

1. **Strict by default, both directions.** Too many and too few are both
   `ARITY-000x` errors (reuse the existing codes/messages where they fit; add a
   variant whose `function` is the bound name or `<anonymous fn>`).
2. **Explicit opt-in for variadics.** If/when a rest parameter is wanted, spell
   it `fn(a, ...rest)` — the array-destructuring parameter already parses
   `...rest`, so the syntax is in the language. Until then, there is no way to
   declare a variadic `fn`, which is fine.
3. **Internal callbacks adapt, not ignore.** Every site in the table above that
   passes a fixed count must do what the for-loop does: inspect
   `fn.ParamCount()` and pass a matching number of arguments, or raise a clear
   error if the count is unsupported. Concretely:
   - Tag dispatch: pass the props dict only when `ParamCount() >= 1`; `fn()`
     components keep working.
   - `.reduce`: accept 1- or 2-param reducers (pass `acc` only for 1-param).
   - The 1-arg sites (`.map`, `.filter`, table methods, markdown walkers,
     `.replace`): require exactly 1 param (or the already-adapting rule), and
     raise `LOOP-0004`-style errors otherwise.
4. **Destructuring parameters** (`fn({a, b})`, `fn([x, y])`) count as one
   parameter each; their internal shape is already lenient by design and is
   out of scope here.
5. Update `functions.md` (remove the "silently ignored" paragraph and the
   warning box), `errors.md` (ARITY row: "builtin/method" → "any function"),
   and add a CHANGELOG entry.

## Risk
This is a breaking change for any existing `.pars` code that (a) calls a
function with extra arguments, or (b) declares a component as `fn()` and relies
on the props dict being dropped. (b) is protected by rule 3. (a) is by
definition a latent bug in the caller. The test suite is the canary: run
`go test ./...` after the change and fix any fixture that was relying on
dropped arguments.

## Out of scope
- Default parameter values (`fn(a, b = 2)`) — a separate feature that would
  naturally relax the "too few" rule. Worth a FEAT if wanted.
- Named/keyword arguments.
