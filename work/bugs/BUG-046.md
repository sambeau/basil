# BUG-046: a kind you could write down but not produce, convert to, or combine

## Summary
Three related gaps around the `time_seconds` kind, found while asking why
`@timeNow` rendered `"01:01"` — a clock that ticks once a minute.

1. **`@timeNow` was `time`.** It is the current moment, which has a second in
   it, and its `.time` property had always returned `"01:01:42"`. Declaring it
   `time` made BUG-045's kind-aware formatting render it without seconds.
2. **`time()` flattened precision.** It ended `timeToDictWithKind(t, "time", env)`
   unconditionally, so `time("14:30:45")` came back as kind `time` and rendered
   `"14:30"` — silently discarding what it was handed. Since nothing else
   produced `time_seconds`, the kind was reachable only by writing a literal.
3. **`&&` rejected it.** `evalDatetimeIntersection` matched `"time"` exactly, so
   `@2026-01-01 && @14:30:45` failed with `Unknown operator: date && time_seconds`
   while the identical expression with `@14:30` worked.

Together: a kind that could be written but not produced, not converted to or
from, and not combined with a date.

## Fix
**`@timeNow` parses as `time_seconds`** (`parseTimeNow`).

**`time()` keeps the precision it is given**, the way the literal parser already
did — two colons means seconds are part of the value — and it now accepts a
datetime value as well as a string, returning its time portion. A `datetime` and
a `time_seconds` both carry a second and keep it; a `time` and a `date` do not.

**`time()` takes `{seconds: …}`** to state the precision outright, following the
options-dictionary convention `datetime()` already uses:

```parsley
time(@14:30, {seconds: true})     // "14:30:00" — kind "time_seconds"
time(@timeNow, {seconds: false})  // "09:05"    — kind "time"
```

Defaulting to *keeping* seconds and requiring `{seconds: false}` to drop them is
the point: silently discarding precision is the behaviour this bug is made of.

**`&&` normalises `time_seconds` to `time`** before its case analysis. Seconds
survive either way — the combining code already copies `Second()`.

## Verification
`TestTimeSecondsIsAFirstClassKind` covers all three: the literal's kind, the four
`time()` parse paths, conversion in both directions, the time portion of a
datetime, and `date && time_seconds` producing a datetime that keeps its 45
seconds.

`TestDatetimeNowLiterals` asserted `@timeNow.kind == "time"` and was updated —
that is the behaviour deliberately changed here, and the comment says so.
