# BUG-030: `isTruthy` uses pointer identity, so non-singleton `false` Booleans are truthy

## Summary
`isTruthy` recognises `false` only by pointer identity with the `FALSE`
singleton. Its fallback type-switch handles `*String`, `*Array`,
`*Dictionary`, `*Integer`, and `*Float` — but has **no `*Boolean` case** — so
any freshly allocated `&Boolean{Value: false}` falls through to
`default: return true`.

Several code paths return fresh Booleans instead of the singletons. The worst
offender is `record.isValid()`, which returns
`&Boolean{Value: len(record.Errors) == 0}`: on a validated record **with
errors**, the result prints as `false` and compares `== false` correctly, but
is **truthy** in every conditional context.

## Reproduction
```parsley
@schema UserMax {
    name: string(min: 2, max: 4)
}
let bad = UserMax({name: "abcdef"}).validate()

bad.isValid()                              // false  (prints correctly)
bad.isValid() == true                      // false  (equality compares .Value)
if (bad.isValid()) "valid" else "invalid"  // "valid"  ← WRONG
let v = bad.isValid()
if (v) "valid" else "invalid"              // "valid"  ← WRONG
```

Compare: `let f = false; if (f) …` behaves correctly, because the literal
evaluates to the `FALSE` singleton.

## Expected
`if (bad.isValid())` takes the else branch. A Boolean's truthiness must depend
on its value, never on which allocation produced it.

## Suspected Location
- `pkg/parsley/evaluator/eval_helpers.go:627` — `isTruthy`: the inner
  type-switch needs `case *Boolean: return v.Value`. (The outer
  `case TRUE / case FALSE` identity checks then become a fast path only.)
- Allocation sites returning fresh Booleans should also use
  `nativeBoolToParsBoolean` (or the singletons) for consistency, e.g.:
  - `methods_record.go:382` — `recordIsValid`
  - `methods_record.go:397` — `recordHasError`
  - `record.go:117`, `record.go:381`
  - `image.go:608`
  - `eval_method_dispatch.go` (multiple `&Boolean{Value: true}` returns)
  - `grep -rn '&Boolean{Value:' pkg/parsley/evaluator/` for the full list

Note the same singleton-identity assumption may exist in other helpers (e.g.
anything doing `obj == TRUE` / `obj == FALSE` or `obj != FALSE`); those sites
should be audited in the same pass.

## Impact / Risk
- **Validation bypass**: the idiomatic guard
  `if (record.isValid()) { save(record) }` in a Basil form handler saves
  records that failed validation. Anything driving control flow off
  `isValid()` / `hasError()` (also `!`, `not`, `&&`, `||`, ternaries, `while`
  conditions) is affected.
- Deeply confusing to debug: the value *prints* as `false` and *compares*
  equal to `false`, but branches as if `true`.
- Existing Go tests miss it because they assert on `Boolean.Value` directly
  rather than going through `isTruthy`.

## Found
While verifying the BUG-029 follow-up (Unicode audit) through the `pars` CLI:
a schema-validation script using `if (bad.isValid()) …` reported an invalid
record as valid even though `.errors()` showed a `MAX_LENGTH` error and a bare
`bad.isValid()` printed `false`.
