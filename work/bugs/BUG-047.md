# BUG-047: the markup was right and nothing was listening

## Summary
`<Part src={…} part-refresh={1000}/>` rendered correct markup —
`data-part-src`, `data-part-view`, `data-part-props`, `data-part-refresh="1000"`
— and the browser did nothing with it, because **the Parts runtime JavaScript
was not on the page**. A page with a Part carried exactly one script: live
reload.

Auto-refresh, lazy loading, `part-load`, cross-part targeting and the
`window.Parts` API were all dead in site mode. The endpoint worked perfectly the
whole time, which is what made it confusing: `curl /shows.part?_view=default`
returned fresh content on every call, so the server looked healthy and the page
looked stuck.

## Cause
Injection was gated on `env.ContainsParts`:

```go
if env != nil && env.ContainsParts {
    output = injectPartsRuntime(output)
}
```

`evalPartTag` sets that flag on the environment evaluating the tag
(`eval_tags.go`), and `NewEnclosedEnvironment` copies it **outer → inner** at
creation. Nothing carries it back up. So the flag lands on a child environment
and the handler, holding the parent, never sees it.

Not "sometimes": a Part is always inside something — a function, a component,
or just the tag that wraps the page — so the flag never arrived. Confirmed by
printing the pointers on a page whose entire body was a single `<Part/>`:

```
DEBUG evalPartTag:   setting ContainsParts on env=0xaf1a7da4000
DEBUG writeResponse: env=0xaf1a602c840 ContainsParts=false
```

## Fix
The gate reads the rendered HTML instead:

```go
func pageNeedsPartsRuntime(html string) bool {
	return strings.Contains(html, "data-part-src=")
}
```

That is the question actually being asked, and unlike a flag threaded through
environments it cannot go out of step with what was rendered. Every Part carries
`data-part-src` — `evalPartTag` writes it unconditionally — and a page that
somehow contains the string without a Part gets a runtime that finds no elements
and does nothing.

`env.ContainsParts` is left in place; it is an exported field and still set,
just no longer trusted for this.

## A second bug, found while verifying
With the runtime finally running, every refresh planted a **live-reload script
inside the Part**. The live-reload middleware injects before `</body>`, falling
back to `</html>`, falling back to appending at the end. A Part fragment has
none of those, so it took the fallback — and the runtime assigns the response
straight into `el.innerHTML`, once a second at `part-refresh={1000}`.

`injectLiveReload` now passes Part fragment requests through untouched,
identified by the `_view` query parameter the runtime always sends and nothing
else does.

## Verification
- Isolated site, routes that actually resolve: `/` and `/plain/` (no Parts) get
  no runtime; `/nested/` (a Part inside a `fn`) gets it.
- The reporter's own page in a real browser: the Part's text went from
  `01:32:13` to `01:33:29` on its own.
- The fragment response is now bare HTML —
  `<section id="tour"><h2>Next shows</h2>01:34:28</section>` — while full pages
  still carry live reload.
- `TestPageNeedsPartsRuntime` and `TestIsPartFragmentRequest`.

## Notes
Two false trails worth recording. The nesting hypothesis — that a Part inside a
function behaved differently from one at the top level — was wrong; nothing
worked, at any depth. And several comparisons early on were meaningless because
the site router was quietly serving `index.pars` for every unmatched path, so
four "different" pages were the same 21,914 bytes. Site routes need a directory
with an `index.pars`, and a trailing slash.

Testing the browser half needs care: the preview pane reports
`document.hidden === true` whatever you do with it, and the runtime deliberately
pauses auto-refresh while a tab is hidden. Overriding the property and
dispatching `visibilitychange` is what let the tick be observed.
