# BUG-044: the same value reported two different days

## Summary
Every way of asking a datetime what day it is must give the same answer. Two did
not. At **00:32 BST on Thursday 27 August** — 23:32 UTC on the 26th — one value
said this:

| Accessor | Value | |
| --- | --- | --- |
| `.iso` | `2026-08-27T00:32:17+01:00` | correct |
| `.day` / `.weekday` / `.date` | `27` / `Thursday` / `2026-08-27` | correct |
| `.fmt("medium")` | `Aug 26, 2026` | **wrong** |
| `.fmt("full")` | `Wednesday, August 26, 2026` | **wrong** |

A page printing a formatted date showed yesterday's. This is not a rare edge: it
is every night between local midnight and UTC midnight in Britain, and **thirteen
hours of every day in New Zealand**, where UTC+13 means the local date is ahead
of UTC for more than half the time.

It surfaced as a flaky test — `TestTimeOnlyUsesCurrentDate` failing for one hour
a night — which is the least alarming way a bug this size could have announced
itself.

## Two causes, independently wrong
**Formatting re-derived the calendar in UTC.** `formatDateWithStyleAndLocale`
rebuilt its `time.Time` from the dictionary's `unix` field and forced the zone:

```go
t = time.Unix(unixInt.Value, 0).UTC()
```

so it printed a different day from the one the value's own fields reported.

**Time-only literals were dated to the UTC day.** `@12:30` takes today's date as
its base, and "today" was `time.Now().UTC()` while `@now` used `time.Now()`. The
comment said "Use current UTC date as the base", so it was deliberate — but it
made a time literal and `@now` disagree about what day it is.

## Fix
Formatting now builds its time with `dictToTime`, the same conversion every other
accessor uses: it reads the stored year/month/day/hour/minute/second, which *are*
the value's wall clock. It labels them UTC, which does not matter, because
formatting reads only those fields and never the zone. A dictionary lacking the
calendar fields falls back to `time.Unix(...).Local()` rather than `.UTC()`.

Time-only literals are dated to `time.Now()`.

**Written-down literals are unchanged and deliberately so.** `@2024-12-25` and
`@2024-12-25T14:30:05` still parse as UTC: a date with no zone written in it
should not acquire one from whichever machine runs the code, and changing that
would silently shift every hard-coded date in every site. Only "today" is a
question about where you are.

## Verification
- `TestDatetime_LocalDateIsConsistent` pins both halves and does **not** wait for
  the clock. It sets `time.Local` to a fixed zone chosen so the local and UTC
  dates differ *right now* whatever the hour — offset `-(h+1)` when the UTC hour
  is ≤ 13, `24-h` when it is ≥ 14, so one of the two always lands on another day
  and neither exceeds the ±14 limit. Confirmed to fail with either fix reverted,
  separately: `@12:30.day = 26, @now.day = 27` for the literal, and
  `@now.fmt("full") = "Wednesday, August 26, 2026" but @now.weekday = "Thursday"`
  for the formatter.
- Full suite green in local BST **inside the window that was failing**, and under
  `TZ=Pacific/Auckland`, `America/Los_Angeles`, `Asia/Kolkata` and `UTC` — zones
  whose local date sits ahead of, behind and level with UTC.

## Notes
`TestTimeOnlyUsesCurrentDate` is kept: its assertion is still true and it costs
nothing. It is no longer the guard, because it only exercises the bug during the
divergence window — a test that can only fail for one hour a day is one that gets
rebased past.

Separately noticed and **not** fixed here: there is no format style that renders
a time. `short`/`medium`/`long`/`full` are all date-only, so `@now.fmt(…)` drops
the time entirely and `@timeNow` — a *time-only* value — formats as a bare date.
`.time` gives `"00:32:17"` and is the only way to display a clock. Worth its own
issue.
