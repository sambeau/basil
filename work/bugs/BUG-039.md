# BUG-039: the documented way to make a dev partner produced a folder that would not start

## Summary
`git clone https://host/.git` is how you set up a dev partner. The getting-started
guide says so, and `basil --init --server` prints the command as its own closing
instruction. But the clone carries the release's `basil.yaml`, which came from the
server and therefore said `auth: enabled: true` — so `basil --dev` in a fresh clone
refused to start:

```
error: creating server: initializing auth: opening auth database:
no authentication database found in this folder (/…/featheredapes/.basil-auth.db)
```

On the server that database lives in `data/`, outside the release. A laptop has no
data directory and no reason to have been given an auth database at all.

Two design constraints make this a real bug rather than a rough edge: a hobbyist
should need little or no configuration for things to work, and the local dev server
running in tandem with a remote one is an essential part of the intended workflow.
The clone path satisfied neither.

## Cause
One fact produces every symptom: **in a clone, `DataDir` defaults to the project
directory**, so everything the server keeps in `data/` tries to live inside the git
working copy.

- `server.go`'s `initAuth` already had a degrade for a missing database, but it was
  gated on `SiteRoot != ""`. Its comment reasoned that "the legacy layout does not
  reach this code: nothing is forced there, so `auth.enabled` false means auth off".
  True of a locally-created folder — and false of a clone, where auth is enabled not
  because anything forced it but because the release's config says so.
- `basil --init --server` wrote two files that are only ever *read* in a clone, and
  wrote both for the server instead. `basil.yaml` asserted `auth.enabled: true`,
  which `config.enforceOperatorOwned` forces on regardless, so the setting bought
  nothing on the server and broke the laptop. `.gitignore` said "nothing else belongs
  here: Basil keeps databases, logs, certificates, caches and uploads in the site's
  data directory, outside this repository" — true of the release directory on the
  server, false of the clone, where `basil --dev` writes `dev_logs.db` beside it.

The design documents consistently describe the **laptop-first** path (`basil --init`
locally, develop, graduate to a server). The server-first path was never walked, even
though init advertises it.

## Fix
1. **`basil --dev` creates a missing auth database; production still refuses.**
   `initAuth` selects `auth.OpenOrCreateDB` in dev mode and keeps `auth.OpenDB`
   otherwise. On a real server a missing auth database means the credentials are
   gone — an emergency to report, not a state to paper over with a new empty one.
2. **One `.gitignore` template for both init modes**, since in both the only reader
   is a working copy. The server-mode file is gone; the local one (which already
   covered `.basil-auth.db*`, `dev_logs.db*`, `*.db*`, certs, keys, logs) is now
   shipped in the starter release too.
3. **The starter release carries no `auth:` block.** A comment in its place records
   that a site root forces authentication on and says why the setting is not written.

### Why create rather than degrade to auth-off
Degrading was the other option and is worse. A site using `auth.protected_paths`
would serve its protected pages **open on the laptop and closed in production** —
you would build and test a members' area that was not one. An empty database gives
every request the same answer production gives: nobody is signed in.

### Why a file rather than an ephemeral in-memory database
The WebAuthn relying-party id is `server.host`, so a passkey registered against the
live site cannot be used against `localhost`. A dev partner needs its own local
credentials, and re-registering a passkey on every restart is not a workflow.
`basil users create` then finds the database already there.

### Why no warning
It would fire on every start of every graduated site and mean nothing to most of
them — the same reasoning `enforceOperatorOwned` already uses for staying silent
about omission.

## Verification
- `TestDevCreatesMissingAuthDatabaseInAClone` and
  `TestProductionStillRefusesAMissingAuthDatabase` (server) pin both halves,
  including that dev does not disable authentication to get there.
- `TestInitCommand_StarterReleaseIsSafeToCloneAndDev` (cmd/basil) pins the two files
  a clone inherits: no `auth:` block, and a `.gitignore` covering what `--dev` writes.
- End to end with the built binary: `basil --init --server` → `git clone` → `basil
  --dev` in the clone serves 200 with no config and no flags, and `git status` is
  clean because the new `.gitignore` covers `dev_logs.db` and its sidecars. Repeated
  with an `auth: enabled: true` block appended, as existing clones have: starts,
  serves 200, creates `.basil-auth.db` mode 0600, still ignored by git.

## Notes
Existing clones keep the old `.gitignore` and `auth:` block until their site
publishes a release built by the new init; fix (1) is what makes them work
regardless, which is why it is the one that matters.

The shared `.gitignore` now ignores `*.db` in the starter release, so a site wanting
to commit a read-only SQLite data file must force-add it. Consistent with what a
locally-created project has always done, and preferable to a laptop's credential
database being offered for commit.
