# BUG-050: a cap at three decimals, hidden by padding

## Summary
`.fmt(n)` on a float rounded to `n` places correctly, then printed only three of
them and padded the rest with zeros:

```parsley
3.14159.fmt(4)      // "3.1420"  — should be "3.1416"
1234.5678.fmt(6)    // "1,234.568000"  — should be "1,234.567800"
```

Every precision above 3 was wrong. The padding is what made it hard to see: the
output has exactly the number of digits you asked for, so it looks deliberate
rather than truncated, and the wrong digits are at the end where nobody checks.

## Cause
`formatNumberWithPrecisionAndLocale` did the rounding itself and then handed the
rounded value to `formatNumberWithLocale`, whose `number.Decimal(value)` caps
fraction digits at three by default. Having lost the digits, it counted what
came back and appended ASCII zeros to make up the width.

The padding carried a second bug of its own. To find the decimal point it
consulted a hard-coded list of three locales that use a comma:

```go
decSep := "."
if locale == "de-DE" || locale == "fr-FR" || locale == "es-ES" {
    decSep = ","
}
```

so `1234.56789.fmt({precision: 4, locale: "de-DE"})` came out `"1.234,5680"` —
the right separator, from the wrong source, on a wrong number. Any other
comma-decimal locale (`it-IT`, `pt-BR`, `nl-NL`, `ru-RU`, …) would have had
zeros appended after a separator the code did not recognise.

## Fix
Ask the formatter for the width instead of correcting it afterwards:

```go
number.Decimal(rounded,
    number.MinFractionDigits(precision),
    number.MaxFractionDigits(precision))
```

That prints the digits and pads short values in one step, with the locale's own
decimal separator and grouping. The three-locale table and the `lastIndexOf`
helper written for it are gone.

The explicit `math.Round` before it stays: it rounds half away from zero, which
is what this function has always done and what a reader expects of `2.5.fmt(0)`,
while `x/text` rounds half to even. Since the value reaching the formatter is
already rounded to `precision`, the formatter's own rounding is a no-op.

The function moved from `methods_numeric.go` to `eval_locale.go`, beside the
other locale formatters it now shares imports with.

## How it got past the tests
Nothing called `.fmt(n)` at any precision anywhere in the suite. The cap sits at
three and the examples people write are `.fmt(2)`, so the docs' own
`3.14159.fmt(4)` was very nearly the first call ever made past it — and it was
made by an auditor reading `numbers.md`, not by a test.

## Verification
`TestFormatPrecision` covers precisions on both sides of the old cap, padding,
half-away-from-zero rounding, the options-dictionary and `.long()` routes, and
two comma-decimal locales.
