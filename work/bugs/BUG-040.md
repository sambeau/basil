# BUG-040: following the manual produced "Undefined component: `Css`"

## Summary
`docs/basil/manual/routing.md` documents the asset-bundle tags as `<Css/>` and
`<Script/>`. The evaluator only recognised `CSS` and `Javascript`, so a layout
written from the manual failed with:

```
Undefined component: `Css`
```

The archived cheatsheet still documents `<CSS/>` and `<Javascript/>`, so the manual
was rewritten to a better pair of names that was never implemented. The existing
tests give the game away: they are called `TestCssTag_EmitsLink` and
`TestScriptTag_EmitsScript` while feeding the evaluator `<CSS/>` and
`<Javascript/>`.

Two things made this worse than a plain naming slip. The tags render an empty
string when there is no bundle, so nothing about the failure suggested "asset
bundling" — and the error pointed at the file that *called* the component rather
than the one containing it (BUG-041), sending the reporter to an unrelated
`<header>` tag in a different file.

## Fix
`evalCustomTag` accepts both spellings:

- `Css` and `Script` — the documented names, and the primary pair. They match the
  TitleCase every other component uses (`<Page/>`, `<Select/>`,
  `<basil.auth.Login/>`) and do not spell JavaScript "Javascript".
- `CSS` and `Javascript` — the original spellings, kept working because a site
  that used them must not break.

`routing.md` gains two notes: that the aliases exist, and that both tags render
nothing when there is no bundle, so they are safe to leave in a layout before any
CSS is written.

## Verification
- `TestBundleTags_BothSpellings` covers all four tags, asserting each returns a
  string rather than an undefined-component error.
- The reporter's own `page.pars`, unmodified, now renders: `<Css/>` and `<Script/>`
  in a `<head>` produce a page instead of a 500.

## Notes
`<BasilJS/>` sits beside these and was not touched: it is spelled the same way in
code and docs.
