# BUG-042: `deployed` and `Deployed` were the same event

## Summary
A successful `basil publish` printed seven lines for a deploy that took five
milliseconds:

```
Pushing 981d02dc02b1 to "live"...
remote: Checking release 981d02dc02b1… ok
remote: deploying 981d02dc02b1
remote: deployed 981d02dc02b1 in 5ms
remote: Deployed 981d02dc02b1 (5ms)
To https://featheredapes.com/.git
   e4cdf16..981d02d  HEAD -> live
Published 981d02dc02b1 to "live".
```

The reporter's question — "is there a difference between `deployed` and
`Deployed`?" — is the whole bug. There is none. They are one event, reported
twice, and the only thing distinguishing them is a capital letter.

## Cause
The deploy engine writes its own progress (`server/deploy/engine.go`: "deploying
<sha>", "deployed <sha> in <d>"). That is correct for `basil deploy` at a shell,
where those lines are the entire output. The receive hook set `eng.Out = stdout`
— the pusher's terminal — and then printed its own summary on top, so the engine
and the hook both narrated the same deploy.

The release id then appeared four times in eight lines: the announcement, the
check, twice more from the two narrators, and again in Git's own ref-update line.

## Fix
Trimmed to what a pusher needs: the id, the check and its verdict, the deploy
and its verdict, and anything that went wrong.

```
Pushing 981d02dc02b1 to "live"...
remote: Checking release 981d02dc02b1… ok
remote: Deploying… done (5ms)
To https://featheredapes.com/.git
   e4cdf16..981d02d  HEAD -> live
```

Three changes:

- **`Engine.Quiet`** suppresses the two routine progress lines and *nothing
  else*. Warnings and notable outcomes — "already live — nothing to do", a
  skipped validation, a failed post-deploy hook, a prune that did not work —
  still go to `Out`, because a caller that suppressed those would be hiding what
  an operator most needs. `basil deploy` at a shell is untouched.
- **The hook adopts pre-receive's partial-line shape**: `Deploying… ` before the
  work, `done (5ms)` on the end of it, so a slow deploy still shows progress. It
  does not repeat the id, which is on the line immediately above and in Git's
  output.
- **`basil publish` drops its closing `Published … to "live".`** The
  announcement already names the release and branch, the hub says it went live,
  and Git prints the ref move in between.

## Verification
- End to end against a real hub: a successful publish prints the four lines
  above, and a release with a parse error still reports the failing
  `file:line:col`, "Release rejected. The live site is unchanged (still …)", the
  refusal, Git's rejection and a non-zero exit.
- `TestFromHook_ReleasePushDeploysAndRecordsPublisher` asserts the new line and
  that the engine's progress does *not* also reach the pusher.
- `TestPublish_SuccessPushesAndStreams` asserts the push is announced once and
  that the closing line has not come back.

## Notes
The server-side lines stay self-sufficient — `Checking release <id>… ok` keeps
its id — because a plain `git push` user sees only those, with no client
announcement above them.
