## 1. Fake Transaction API

| | |
|---|---|
| **Severity** | 🔴 Critical |
| **Status** | `resolved` — fixed in FEAT-136 |
| **Spec** | `work/specs/FEAT-136.md` |
| **Location** | `pkg/parsley/evaluator/eval_method_dispatch.go` L11–45 |

### Finding

~~The `db.begin()`, `db.commit()`, and `db.rollback()` methods exist and are callable, but they **do not issue real SQL transactions**. They toggle a boolean flag (`conn.InTransaction`) without calling `sql.DB.Begin()`, `sql.Tx.Commit()`, or `sql.Tx.Rollback()`.~~

### Resolution (FEAT-136)

Option 1 was implemented. `begin()`, `commit()`, and `rollback()` now issue real SQL transactions:

- `begin()` calls `conn.DB.Begin()`, stores the resulting `*sql.Tx` in `conn.Tx`, and returns `DB-0007` if already in a transaction.
- `commit()` calls `conn.Tx.Commit()`, clears `conn.Tx`, and returns `DB-0015` on failure.
- `rollback()` calls `conn.Tx.Rollback()`, clears `conn.Tx`, and returns `DB-0019` on failure.
- All three query/execute operators (`<=?=>`, `<=??=>`, `<=!=>`) route through `conn.Tx` when active, via `connQuery`/`connExec`/`connQueryRow` helpers.

Integration tests covering commit and rollback semantics were added in `pkg/parsley/tests/database_advanced_test.go`.

### 2a. TestDatabaseShutdown

| | |
|---|---|
| **Location** | `server/database_test.go` ~L195 |
| **Error** | `listen tcp 127.0.0.1:8080: bind: address already in use` |

The test hardcodes port 8080. It fails when anything else is using that port (another test, a dev server, etc.). Should use `:0` for a random port or use `httptest.NewServer`.

### 2b. TestSiteHandler_RootPath

| | |
|---|---|
| **Location** | `server/site_test.go` ~L351 |
| **Error** | `security: file read restricted` when importing `@~/components/header.pars` |

The test creates a site directory and a sibling `components/` directory. The site handler's security policy restricts reads to the site directory, so `@~` (handler root) can't reach the component file. This may indicate a **real user-facing bug**: site-mode projects that organise shared components outside the site directory will hit this restriction.

### Action

Both need investigation. 2b in particular may reveal a security policy design issue in site mode — either the test setup is wrong, or the security sandbox is too restrictive for the intended `@~` semantics.

## 3. Config YAML Consistency

| | |
|---|---|
| **Severity** | 🟡 Should fix |
| **Status** | `open` |
| **Spec** | — |
| **Location** | `server/config/config.go` |

### Findings

#### 3a. Naming inconsistency: `maxAge` vs `max_age`

The CORS config uses camelCase `maxAge` while every other config key uses `snake_case`:

| Key | Section | Style |
|-----|---------|-------|
| `max_age` | session | snake_case ✅ |
| `max_size` | dev (log) | snake_case ✅ |
| `maxAge` | cors | **camelCase** ❌ |

This is a YAML-level breaking change to fix (existing config files would break), but it should be done before 1.0 while we still can.

#### 3b. Orphaned top-level keys

Several keys sit at the top level but logically belong together or under a parent:

| Key | Current | Suggestion |
|-----|---------|------------|
| `sqlite` | top-level string | `database.sqlite` or `database.path` (future-proofs for other drivers) |
| `public_dir` | top-level string | `server.public_dir` or keep top-level but document why |
| `site` | top-level string | Fine — it's a major mode selector |
| `site_cache` | top-level duration | Should be `site.cache` if `site` becomes a section, or at least adjacent to `site` |

The `sqlite` key is the most concerning for future-proofing. If server-level Postgres support is ever added, the config shape becomes awkward.

#### 3c. Go naming: `HttpOnly`

`SessionConfig.HttpOnly` should be `HTTPOnly` per Go conventions (HTTP is an initialism). The YAML tag `http_only` is fine. Minor, but visible in the Go API.

### Recommendation

Fix 3a (rename `maxAge` → `max_age`) and 3c (`HttpOnly` → `HTTPOnly`) at minimum. Consider 3b as part of a broader config design discussion — do we want a `database:` section?

## 4. Standard Library Organisation

| | |
|---|---|
| **Severity** | 🟡 Should fix |
| **Status** | `open` |
| **Spec** | — |
| **Location** | `pkg/parsley/evaluator/stdlib_table.go` (module registry) |

### Findings

#### 4a. Server-dependent modules in `@std/` namespace

Three `@std/` modules require the Basil server runtime and fail or silently no-op without it:

| Module | Requires | Behaviour Without Server |
|--------|----------|--------------------------|
| `@std/dev` | `env.DevLog` (server-only) | All methods are silent no-ops |
| `@std/html` | `PreludeLoader` (server-only) | Returns error: "prelude not initialized" |
| `@std/api` | `BasilCtx` (server-only) | Auth wrappers won't function correctly |

These should be in the `@basil/` namespace, consistent with `@basil/http`, `@basil/auth`, `@basil/session`, `@basil/csrf`.

The `@std/dev` → `@basil/log` rename is already in the backlog (#57) but should be promoted to 1.0 scope. `@std/html` and `@std/api` have the same problem.

#### 4b. Module naming inconsistency

| Module | Name Style | Consistent? |
|--------|-----------|-------------|
| `@std/math` | lowercase | ✅ |
| `@std/valid` | lowercase | ✅ |
| `@std/schema` | lowercase | ✅ |
| `@std/id` | lowercase | ✅ |
| `@std/hash` | lowercase | ✅ |
| `@std/api` | lowercase | ✅ |
| `@std/dev` | lowercase | ✅ |
| `@std/mdDoc` | **camelCase** | ❌ |
| `@std/html` | lowercase | ✅ |

`@std/mdDoc` is the only camelCase module name. Should be `@std/mddoc` or `@std/md`.

#### 4c. Module inventory

For reference, here is the complete stdlib as of this audit:

**`@std/` namespace** (pure Parsley, should work in CLI and server):
- `math` — Mathematical functions and constants
- `valid` — Validation predicates (UUID, credit card, postal codes, etc.)
- `schema` — Schema definitions and validation
- `id` — ID generation (UUID, ULID, NanoID, CUID)
- `hash` — Cryptographic hashing (SHA-256, SHA-512, MD5, SHA-1)
- `mdDoc` — Markdown document builder ⚠️ naming

**Should move to `@basil/`:**
- `dev` → `@basil/log` or `@basil/dev`
- `html` → `@basil/html`
- `api` → `@basil/api`

**`@basil/` namespace** (require Basil server):
- `http` — Request/response access
- `auth` — Authentication
- `session` — Session management
- `csrf` — CSRF tokens

### Recommendation

1. Rename `@std/mdDoc` → `@std/mddoc` (or `@std/md`)
2. Move `@std/dev`, `@std/html`, `@std/api` to `@basil/` namespace
3. Add deprecation aliases for the old names that log a warning and delegate to the new name

## 5. Method Dispatch Inconsistency

| | |
|---|---|
| **Severity** | 🟡 Should fix |
| **Status** | `open` |
| **Spec** | — |
| **Location** | `pkg/parsley/evaluator/method_registry.go`, `methods.go`, `eval_method_dispatch.go` |

### Finding

Two coexisting method dispatch systems:

**New: Declarative `MethodRegistry`** (5 types migrated)
- `string` — `methods_string.go`
- `integer` — `methods_numeric.go`
- `float` — `methods_numeric.go`
- `money` — `methods_money.go`
- `unit` — `methods_unit.go`

Benefits: self-documenting, arity checked automatically, introspectable via `pars describe`, fuzzy-matched "did you mean?" error messages.

**Old: Hand-coded `switch` statements** (~15+ types)
- `array` — `methods.go` (378+ lines of switch cases)
- `dictionary` — `methods.go` (202+ lines)
- `boolean` — `methods.go`
- `null` — `methods.go`
- `datetime` — `methods.go`
- `duration` — `methods.go`
- `path` — `methods.go`
- `url` — `methods.go`
- `regex` — `methods.go`
- `file` — `methods.go`
- `dir` — `methods.go`
- `request` — `methods.go`
- `response` — `methods.go`
- `DBConnection` — `eval_method_dispatch.go`
- `SFTPConnection` — `eval_network_io.go`
- `SFTPFileHandle` — `eval_network_io.go`
- `session` — `stdlib_session.go`
- `table` — `stdlib_table.go`
- `record` — `methods_record.go`
- `DSLSchema` — `stdlib_dsl_schema.go`

The old types have hand-rolled arity checking, don't appear correctly in `pars describe`, and produce less helpful error messages.

### Impact

- `pars describe array` (probably the most commonly queried type) won't show methods from the registry.
- Error messages for unknown methods are inconsistent between registry and switch-based types.
- New method additions require different patterns depending on the type.

### Recommendation

Migrate `array` and `dictionary` as highest priority — they're the most commonly used types. The "dictionary-like" types (datetime, duration, path, url, regex, file, dir) share a structural pattern and could be migrated together. Server-specific types (DBConnection, SFTP, session) are lower priority.

## 6. Parsley–Basil Coupling

| | |
|---|---|
| **Severity** | 🟢 Nice to have |
| **Status** | `open` |
| **Spec** | — |
| **Location** | `pkg/parsley/evaluator/evaluator.go` L660–686 |

### Finding

The `Environment` struct has **13 Basil-specific fields** that are all individually propagated in `NewEnclosedEnvironment`:

```
DevLog, BasilCtx, ServerDB, FragmentCache, AssetRegistry, AssetBundle,
BasilJSURL, HandlerPath, DevMode, ContainsParts, FormContext, PLNSecret
```

Additionally:
- `PreludeLoader` in `stdlib_html.go` is a package-level function pointer set by the server — a reverse-dependency workaround.
- `buildBasilContext()` in `server/handler.go` constructs a Parsley dictionary with server state, mixing Go types and AST expressions.

### Risk

Low for 1.0 — it works. But:
- Adding a new server feature that needs evaluator access requires touching `Environment`, `NewEnclosedEnvironment`, `buildBasilContext`, and the handler — four files for one change.
- Forgetting to propagate a field causes subtle bugs in nested scopes (closures, module imports).

### Recommendation

Consider grouping the server-specific fields into a single `ServerContext` struct:

```go
type ServerContext struct {
    DevLog        DevLogWriter
    BasilCtx      Object
    ServerDB      *DBConnection
    FragmentCache FragmentCacher
    // ... etc
}
```

Then `Environment` has one field (`Server *ServerContext`) and `NewEnclosedEnvironment` has one assignment. This is a refactor-only change with no user-facing impact.

Not blocking for 1.0, but reduces the fragility of the current approach.

## 7. Database Drivers

| | |
|---|---|
| **Severity** | 🟡 Should fix (documentation) |
| **Status** | `partially resolved` — placeholder rewriting fixed in FEAT-135/FEAT-136; documentation recommendation still open |
| **Spec** | `work/specs/FEAT-135.md`, `work/specs/FEAT-136.md` |
| **Location** | `pkg/parsley/evaluator/drivers.go`, `drivers_test.go` |

### Finding

Three database drivers are available:

| Driver | Registered | Integration Tested | Used in Production |
|--------|------------|-------------------|-------------------|
| SQLite | ✅ `modernc.org/sqlite` | ✅ Extensive | ✅ Primary driver |
| PostgreSQL | ✅ `github.com/lib/pq` | ❌ Driver registration only | Unknown |
| MySQL | ✅ `github.com/go-sql-driver/mysql` | ❌ Driver registration only | Unknown |

The `drivers_test.go` file confirms the drivers are registered with `database/sql`, but there are no tests that actually connect to a Postgres or MySQL database, execute queries, or test type mapping.

The connection cache (`connection_cache.go`) and query execution code (`eval_database.go`) use the generic `database/sql` interface, so they should work across drivers in theory. But there may be driver-specific issues with:
- Type mapping (e.g., SQLite's dynamic typing vs Postgres's strict typing)
- ~~Parameter placeholder syntax (`?` vs `$1`)~~ — **resolved**: `sqlPlaceholder()` and `rewriteNamedParams()` already emit `$N` for SQLite/PostgreSQL and `?` for MySQL (implemented in FEAT-135, extended to `<SQL>` named params in FEAT-136)
- `LastInsertId()` behaviour (SQLite-only in current code — line 130 of `eval_method_dispatch.go`)
- The `createTable` method builds SQL that may not be dialect-portable

### Recommendation

1. ⬜ **Document clearly** that SQLite is the tested/supported driver for 1.0, and Postgres/MySQL are "provided but not integration-tested" — not yet done in `docs/parsley/manual/features/database.md`
2. ⬜ Review the `createTable` SQL generation for dialect compatibility
3. ✅ The `lastInsertId` method already errors for non-SQLite drivers — good
4. ✅ Parameter placeholder rewriting handles all three drivers — resolved in FEAT-135/FEAT-136
5. ⬜ Backlog item #113 (embedded Postgres for tests) remains deferred — reasonable

## 9. Package Naming & Structure

| | |
|---|---|
| **Severity** | 🟢 Nice to have |
| **Status** | `open` |
| **Spec** | — |

### 9a. `format` vs `formatter` packages

| Package | Path | Contents | Purpose |
|---------|------|----------|---------|
| `format` | `pkg/parsley/format/` | 6 files | Parsley code formatter (`pars fmt`) |
| `formatter` | `pkg/parsley/formatter/` | 1 file (`html.go`) | HTML pretty-printing utility |

The `formatter` package contains a single file that pretty-prints HTML output. The name is confusingly close to `format`. Options:
- Merge `formatter/html.go` into `format/` (it's small enough)
- Rename `formatter` → `htmlformat` or `htmlutil`

### 9b. Evaluator package size

The `pkg/parsley/evaluator/` package contains **78 Go files totalling ~55,000 lines**. This is a single flat package that handles:
- Object type definitions
- Environment and scope management
- The main `Eval()` function (6,164 lines in `evaluator.go` alone)
- All method dispatch (3,333 lines in `methods.go`)
- All stdlib modules
- Database operations
- Network I/O
- Template rendering
- Unit/money arithmetic
- Form binding
- Markdown generation
- and more

This isn't a blocking issue — it works — but it makes the codebase harder to navigate and reason about. The `evaluator.go` file in particular does too many things.

### Recommendation

No action required for 1.0. Note as a post-1.0 refactoring target. If we do split, a natural boundary would be:
- `evaluator/` — core Eval, Object types, Environment
- `evaluator/methods/` or `stdlib/` — method implementations and stdlib modules
- `evaluator/database/` — DB connection, query execution, DSL

## 10. Large Files & Embedded Assets

| | |
|---|---|
| **Severity** | 🟢 Nice to have |
| **Status** | `open` |
| **Spec** | — |

### Finding

`server/handler.go` contains ~560 lines of inline JavaScript (the Parts runtime) as a Go string constant (`partsRuntimeScript`, lines 1279–1842). This JavaScript:
- Handles partial page updates (Part components)
- Manages WebSocket-like communication
- Is difficult to maintain as a string (no syntax highlighting, no linting, no minification)

### Recommendation

Consider extracting to an external `.js` file loaded via `embed.FS` at build time. Go's `//go:embed` directive makes this straightforward and would enable:
- Proper JS syntax highlighting and linting
- Minification as a build step
- Easier testing of the JS in isolation

Not blocking for 1.0.

## 11. Packages Without Tests

| | |
|---|---|
| **Severity** | 🟢 Nice to have |
| **Status** | `open` |
| **Spec** | — |

### Finding

Six packages have no test files at all:

| Package | Risk | Notes |
|---------|------|-------|
| `pkg/parsley/parser` | Medium | Heavily tested indirectly via `pkg/parsley/tests/` integration tests. Parser-specific error messages and edge cases aren't directly tested. |
| `pkg/parsley/ast` | Low | Data structure definitions — mostly tested through parser and evaluator. |
| `pkg/parsley/formatter` | Low | Single file, HTML formatting utility. |
| `pkg/parsley/locale` | Low | Locale data tables. |
| `pkg/parsley/repl` | Low | Interactive REPL — hard to unit test, exercised manually. |
| `server/auth/email` | Medium | Email templates — untested HTML generation for verification emails. |

### Recommendation

`parser` and `auth/email` are the most meaningful gaps. The parser is the project's most complex component after the evaluator — while integration tests exercise the happy path extensively, parser error recovery and error message quality are not directly tested.

`auth/email` generates HTML emails that users receive. Template bugs (broken links, missing variables) would be embarrassing in production.
